# TCP_NODELAY のデプロイと GraalVM の評価 — 2026-10-27

過去のデプロイ記録です。[現在のデプロイと容量の記録](DEPLOYMENT_CAPACITY_2026-10-27.ja.md) が、以下の現在のリリースとロールバック情報を置き換えます。以前のサーバーリリースはすべて削除されています。

## 選択したアプリケーション

アプリケーションのコミット `9207f12` は TCP_NODELAY を恒久化し、キャッシュした Polyglot の `Engine` と `Source` をルーム間で共有します。各ルームは独自の制限付き `Context`、直列化されたアクセス、独立した対戦状態を保ちます。Context は通常の破棄と初期化の失敗で閉じ、共有エンジンはアプリケーションとともに閉じます。起動ログは実際のランタイム実装を示します。

Polyglot とコミュニティの JavaScript ライブラリを 24.2.2 から 25.0.5.0.2 に更新しました。OpenJDK 21 でコンパイルと実行に合格しており、OpenJDK 21 が本番ランタイムのままです。本番サービスには JVMCI や GraalVM のチューニングフラグを追加していません。既存の 512 MiB のメモリ上限と 2 ルームの容量は変わりません。

このリリースには `cdf65b2` の新しいメニューとキャラクター選択の変更が含まれ、パッケージ前に取得してマージしました。共有のバトルルールとプロトコルはバージョン 12 のままです。

アップロードしたチェックサムは有効化の前に一致しました。稼働中のプロセスが `/usr/lib/jvm/java-21-openjdk-amd64/bin/java` を使っていることを確認しました。再起動後に有効なソケットオプションを読むと、観測した 30 本のバックエンド接続すべてで `TCP_NODELAY=1` が確認されました。この設定は一時的なソケット変更ではなく、アプリケーションビルダーに由来します。

## GraalVM の比較

分離ベンチマークでは、AliCloud ホスト上の 3 つの構成すべてに同じバックエンド候補を使いました。別々の一時サービスユニットが同じ 512 MiB のメモリ上限を適用し、サービスの swap を無効にし、タスクを 96 に制限しました。そのホスト上の 4 つのポータブル Node クライアントが、ループバックポート 8181 経由で 1v1 と 3v3 のルームを同時に動かしました。このポートは外部に公開していません。CPU とメモリのサンプルはバックエンドサービスの cgroup から取得し、チェッカーはその外側で実行しました。

当初のワークステーション駆動の試行は、接続が中断して破棄しました。報告する比較はサーバー側クライアントを使い、測定ウィンドウ中はサンプリングプロファイラーを動かしていません。各測定ウィンドウは 120 秒でした。OpenJDK と既定の GraalVM は 60 秒のアクティブなウォームアップ、制限付き GraalVM は 120 秒です。これらは有限の起動/負荷ウィンドウであり、漸近的に完全にウォームアップした JIT 性能の証明ではありません。

Oracle の公式ダウンロードエンドポイントは GraalVM 25.0.4+7.1 を返し、アーカイブの SHA-256 は `76007c309f821aaf435bce63162ea0395587fc77350801c81643fe7feea37276` でした。テストしたのはまさにこのビルドです。古い 24.2.2 の Polyglot ライブラリでは、Java 25 はバージョン非互換のためインタープリター実行に戻りました。更新後のライブラリはバイパスフラグなしでランタイムのバージョン検査に合格し、`Oracle GraalVM` と報告しました。

| 測定結果                               |   OpenJDK 21 |   既定の GraalVM |                               制限付き GraalVM |
| -------------------------------------- | -----------: | ---------------: | ---------------------------------------------: |
| 平均バックエンド CPU、論理コア         |        0.744 |            1.656 |                                          1.618 |
| ピークのサービスメモリ                 |    317.0 MiB |       約 512 MiB |                                      507.8 MiB |
| クライアントあたりのスナップショット数 |  7,144–7,158 |      3,843–4,955 |                                    7,151–7,161 |
| サーバー更新作業 p95                   | 3.56–3.69 ms |     6.89–8.32 ms |                                   3.06–3.46 ms |
| 測定実行中の予期しないクローズ         |            0 |                3 |                                              0 |
| サービスの結果                         |         合格 | 配信チェック失敗 | 測定ウィンドウ後にメモリ上限で kill されました |

既定の構成は既存の 64/256 MiB の Java ヒープと 64 MiB のコードキャッシュ設定を使いました。制限付きの構成は次を使いました：

```text
-Xms64m -Xmx160m -XX:ReservedCodeCacheSize=96m
-XX:-UseJVMCICompiler -XX:+EnableJVMCI
-Dlibgraal.Xmx=128m -Dpolyglot.engine.CompilerThreads=1
--enable-native-access=ALL-UNNAMED
```

制限付きの構成は Java/Scala に HotSpot のコンパイラーを残しつつ、ゲストの JavaScript の Graal コンパイルを許可しました。短いクライアント配信チェックには合格しましたが、その後のサービス監視が 06:44:49 アジア/上海 に OOM kill を捉えました。したがってチェッカーが正常終了したことは、これを採用する十分な根拠ではありませんでした。

最適化ランタイムは実在しました。別の診断トレースが 71 件の完了した最適化イベントを記録し、そこには `simulation.js` のメソッドも含まれます。決定論的なシナリオは 12,800 の固定シミュレーションステップで全 16 キャラクターをカバーしました。Node、OpenJDK、GraalVM は同じチェックポイント/イベントのダイジェストを生成しました：

```text
e316a8c505dcfb71267ebcb5ae25fb8a71889312fc42d9d34c4ea298254e14b0
```

GraalVM は採用しませんでした。テストしたワークロードでは 2 倍以上の CPU を消費し、メモリの余裕が不十分で、制限付きの構成では最終的にサービスのメモリ上限で kill されました。更新作業 p95 のわずかな低下はこれらのコストに見合いません。この結果はこの 2 vCPU ホスト上のこれらの構成に関するものであり、すべての GraalVM 構成やより大きなホストでも同じになるという証明ではありません。ランタイムコンパイルとエンジン/ソースの共有については [GraalVM の埋め込みドキュメント](https://www.graalvm.org/latest/reference-manual/embed-languages/)、ディストリビューションとチェックサムについては[公式ダウンロードページ](https://www.graalvm.org/downloads/) を参照してください。

## コールドスタートの調査

TCP のスタールを取り除いた後でも、コールドのブラウザーチェックには初回対戦の JVM ウォームアップが大きく現れました。あるプロトタイプは HTTP をバインドする前に、ロスター全体に対して決定論的で分離された戦闘ウォームアップを実行しました。21.3 秒で完了しメモリ上限内に収まりましたが、最初の 30 秒の 4 クライアントチェックでは 1 クライアントあたり 751–884 スナップショットしか配信できず、サーバー更新 p95 は約 15.6–16.2 ms でした。配信基準に合格しなかったため、選択したリリースの確定前に削除しました。そのプロトタイプのウォームアップ API や起動遅延はデプロイしていません。

コールドの初回対戦の挙動は依然として制限です。TCP_NODELAY がコンパイル/スケジューリングのスタールを直すと推測してはいけません。また、READY、ラウンド遷移、ヒットフリーズの遅延を転送レイテンシーと混同しないでください。今後の作業では、別のウォームアップ方針を導入したりランタイム/メモリの予算を変えたりする前に、コールドのコンパイルとスケジューラーの負荷を切り分けるべきです。

## 検証

`npm run check`、`npm run check:backend`、`npm run package:server`（`npm run build` を含む）、`npm run build:pages` に合格しました。Pages ビルドは `/mygo-fighter/` の下で読み込まれプレイでき、失敗したリソース応答やブラウザーコンソールのエラーはありませんでした。279 個の公開実行時メディアパスはすべてマニフェスト、コンテンツ範囲、キャッシュヘッダーのチェックに合格しました。

2 つの分離した公開ブラウザーコンテキストがルームを作成/参加し、キャラクターを選択し、ダメージを与え、一時停止/再開し、ゲストをリロードし、保持されたセッションを再開しました。ゲストは 110 HP になり、セッションはリロードを越えて存続しました。JavaScript のページ例外もブラウザーコンソールのエラーも観測されませんでした。これらのコールドの機能チェックは、クリーンなレイテンシーベンチマークとして提示するものではありません。

選択した本番リリースは、60 秒のアクティブなウォームアップ後に、2 つの同時ルームの 4 クライアントで公開 HTTPS/WSS 経由 900.68 秒を完了しました。チェッカーは AliCloud ホストで動かし、通常の証明書検証で公開ホスト名に到達しました。したがってその RTT は開発マシンの WAN 経路の測定値としては使いません。

各クライアントは 53,900–53,940 スナップショットを受信しました。予期しない切断、プロトコルエラー、サービスの再起動はありませんでした。ダメージ、3v3 のリザーブ進行、イベント ID の一致に合格しました。ピアは 1v1 ルームで 3,541 件、3v3 ルームで 3,328 件の一致する一意のイベントを観測しました。平均バックエンド CPU は 0.687 論理コア、ピークのサービスメモリは 290.5 MiB、サーバー更新作業 p95 は 2.45–2.87 ms でした。

4 つの検証セッションはすべて、その後に明示的にルームを離れました。続いて開発マシンからの別の 60.07 秒の 4 クライアント戦闘測定も合格し、予期しないクローズやプロトコルエラーはありませんでした：

| クライアントから観測した WAN 指標        | 以前の元設定の対照 | デプロイ後の `9207f12` |
| ---------------------------------------- | -----------------: | ---------------------: |
| RTT p50                                  |       48.8–50.8 ms |             8.9–9.6 ms |
| RTT p95                                  |       52.1–54.4 ms |           16.4–20.0 ms |
| スナップショット到着間隔 p95             |       57.6–58.2 ms |           19.1–19.6 ms |
| 入力送信 → 返却状態で観測された受信、p95 |       64.6–65.9 ms |           29.5–32.0 ms |
| サーバー更新作業 p95                     |       2.34–2.41 ms |           3.64–3.75 ms |

以前の対照は交互の移動を使い、デプロイ後の実行は戦闘を使い、しかも後に行われました。これらは観測された運用結果であり、すべての差が 1 つのコード変更に由来するという主張ではありません。[以前の監査](DEPLOYMENT_PERFORMANCE_2026-10-26.ja.md) にある先行の同一接続での off/on/off 実験が、約 40 ms の転送スタールの除去についてより強い因果的証拠を与えます。

WAN サンプルは 1 クライアントあたり 3,674–3,676 スナップショットを受信しました。そのセッションも明示的に離れ、両方のルームを解放しました。コールドスタートの測定と意図的なゲームプレイのフリーズは、ウォームアップ後の転送レイテンシー改善に関する主張には含めません。

生のスクリプト、レポート、コンパイラーのトレースは無視対象の `output/runtime-optimization/` に、スクリーンショットは `output/playwright/` にあります。削除されたテストスイートは復元していません。ランタイム比較用のユニットは一時的なもので、本番は元の Java/サービスメモリ設定を使い続けています。

## 運用

現在のリリースの `deployment.json` は、アプリケーションのコミット、アーカイブのチェックサム、選択したランタイム、検証状態を記録します。ヘルスは `/api/health` で引き続き利用できます。以前のアプリケーションに戻すには次を実行します：

```sh
ssh alicloud 'sudo bash /opt/mygo-fighter/rollback.sh'
```

バージョンを切り替えると一時的な対戦は終了します。後からのドキュメントのみのコミットは、アプリケーション成果物や記録されたアプリケーションのコミットを変えません。
