# ゲームプレイのパフォーマンス

現在のプロトコルは 24 で、3 人乱闘と[追加のカスタムルール](CUSTOM_PLAY_EXPANSION_2026-10-29.ja.md)を含みます。[2026-10-29 の LAN スタッター調査](LAN_STUTTER_2026-10-29.ja.md)には、最新のデコード済み画像、クライアント再生、ターゲティングの修正と、ブラウザで実測した前後比較が記録されています。クライアントを揃えてホストを更新・再起動してください。[バックエンドのルームスケーリング監査](BACKEND_SCALING_2026-10-27.ja.md)は、プロトコル 15 におけるアイドルルームのスケジューリング、フレームの共有、アロケーション削減を扱っています。以下の以前の測定は元のプロトコル文脈を保っています。

## 実装済みの最適化

### Canvas レンダリング

- 論理シーンは 960 × 540 のままです。バッキング解像度はデバイスピクセル比で上限を設け、1、1.25、1.5、2 の間で適応します。描画コストが 12 ms を超える状態、またはフレーム周期が 24 ms を超える状態が続くと画質を下げます。復帰には、描画コスト 4 ms 未満かつフレーム周期 20 ms 未満の健全なフレームが 240 個必要です。フレーム圧力のフィードバックが必要なのは、キャッシュされた canvas がネイティブのラスタ処理を JavaScript の描画呼び出しより後に遅延させることがあるためです。
- ファイターのアトラスフレームは、最終的なデバイスピクセルサイズに近い形で遅延して事前ラスタライズされます。LRU は 64 エントリ、8 Mi ピクセル（RGBA 換算で約 32 MiB）に制限されます。ヒットのたびに現在のフレームアンカー、アニメーション、論理スケールが保持されます。ファイター、大きなモーション、ダッシュ、ブリンクの各パスはネイティブ画像とキャッシュ canvas の両方を受け付けます。
- 画像のデコードは、対戦準備中は同時 2 ロードに制限されたままです。準備後、未使用のデコード済み画像は可能な範囲で 384 MiB の予算まで削減されます。現在のファイターと控えが必要とするアートが破棄されることはありません。

### オンライン転送と状態の調整

- プロトコル 11 は、60 Hz の状態パケットから重複していた 2 秒分のイベント履歴と重複したトップレベルの入力カウンターを削除しました。`inputState` が正規のリプレイメタデータです。
- 空でないイベントバッチは、既存の順序付きで有界な制御レーンを使います。状態は最新値のみのままです。制御のオーバーフローは socket を閉じ、表示上の手がかりを黙って捨てる代わりに、既存の一時停止/再接続による復旧を強制します。
- クライアントは、generation、epoch、サーバー時刻が状態と一致するまでイベントバッチを保持し、その後各イベント ID を 1 回だけ消費します。準備、ロビー、再接続の遷移は保留中のバッチを消去します。
- 予測は必要なリプレイ前クローンを保持します。`GameRuntime` にあった 2 つ目の権威クローンは削除されました。
- `?diagnostics=1` の場合、パケットサイズは添付イベントフレームを含む正確な UTF-8 ワイヤサイズです。通常のプレイでは UTF-8 のスキャンも JSON の再シリアライズも行いません。`inputReceivedMs` と `inputAppliedMs` は、クライアントの送信から権威側の受信/適用までを（返却された状態で観測された時点で）測ります。ヒットフリーズは正当に適用を遅らせることがあります。`serverUpdateMs` はルーム/カーネル処理を対象とし、最終的な socket の書き込み/到達は依然として含みません。不変のフレームは自身より後の書き込み完了時刻を含めません。

### オーディオ

- オーディオのロック解除は、112 個すべてのクリップを取得・デコードしなくなりました。重要な画像の読み込み後、選択されたファイターと控えから到達可能なキューだけをウォームアップします。それ以外のキューは初回使用時に読み込みます。
- 同時に読み込むクリップは最大 4 つです。デコード済み PCM は 64 MiB の LRU を使い、アクティブな source node は破棄されたバッファを安全に保持します。保留中の読み込みは、既存の停止、ミュート、一時停止、ラウンド、破棄によるキャンセルの挙動に従います。

## TCP_NODELAY の恒久化とランタイム評価

アプリケーション `9207f12` は TCP_NODELAY を恒久的に有効化し、ルームごとのコンテキストを保ったままエンジン/ソースキャッシュを共有し、Polyglot ライブラリを更新します。[2026-10-27 のランタイム評価](RUNTIME_OPTIMIZATION_2026-10-27.ja.md)には、GraalVM との比較と、512 MiB のサービス予算で OpenJDK 21 を選び続ける理由が記録されています。
