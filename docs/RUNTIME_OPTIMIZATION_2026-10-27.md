# TCP_NODELAY 部署与 GraalVM 评估 — 2026-10-27

历史部署记录。[当前部署与容量记录](DEPLOYMENT_CAPACITY_2026-10-27.md) 取代下文中的当前发布与回滚信息；所有更早的服务器发布均已删除。

## 选定的应用

应用提交 `9207f12` 让 TCP_NODELAY 永久生效，并在各房间之间共享一个缓存的 Polyglot `Engine` 与 `Source`。每个房间保留各自受限的 `Context`、串行化访问与独立的对局状态。Context 在正常释放与初始化失败时关闭；共享引擎随应用一起关闭。启动日志会标明实际使用的运行时实现。

Polyglot 与社区 JavaScript 库从 24.2.2 更新到 25.0.5.0.2。它们在 OpenJDK 21 上通过了编译与执行，而 OpenJDK 21 仍是生产运行时。没有向生产服务添加 JVMCI 或 GraalVM 调优参数。既有的 512 MiB 内存上限与双房间容量保持不变。

本次发布包含来自 `cdf65b2` 的较新菜单与选人改动，在打包前已抓取并合并。共享战斗规则与协议仍为版本 12。

## GraalVM 对比

隔离基准在阿里云主机上为三种配置使用同一个后端候选。独立的临时服务单元都执行相同的 512 MiB 内存上限、禁用服务 swap，并把任务数限制为 96。该主机上的四个便携式 Node 客户端通过环回端口 8181 同时压测 1v1 与 3v3 房间。该端口从未对外公开。CPU 与内存采样来自后端服务的 cgroup；检查器运行在其之外。

最初由工作站驱动的尝试在连接被中断后废弃。报告中的对比使用服务端客户端，并在测量窗口内不开启采样分析器。每个测量窗口持续 120 秒。OpenJDK 与默认 GraalVM 有 60 秒主动预热；受限 GraalVM 获得 120 秒。这些是有限的启动/负载窗口，而不是对渐近式完全预热 JIT 性能的证明。

Oracle 官方下载端点返回 GraalVM 25.0.4+7.1，归档 SHA-256 为 `76007c309f821aaf435bce63162ea0395587fc77350801c81643fe7feea37276`。测试的正是该构建。使用旧的 24.2.2 Polyglot 库时，Java 25 因版本不兼容而回退到解释执行。更新后的库在没有绕过标志的情况下通过了运行时版本检查，并报告 `Oracle GraalVM`。

| 测量结果             |   OpenJDK 21 | 默认 GraalVM |             受限 GraalVM |
| -------------------- | -----------: | -----------: | -----------------------: |
| 平均后端 CPU，逻辑核 |        0.744 |        1.656 |                    1.618 |
| 峰值服务内存         |    317.0 MiB |   约 512 MiB |                507.8 MiB |
| 每客户端快照数       |  7,144–7,158 |  3,843–4,955 |              7,151–7,161 |
| 服务端更新工作量 p95 | 3.56–3.69 ms | 6.89–8.32 ms |             3.06–3.46 ms |
| 测量运行中的意外关闭 |            0 |            3 |                        0 |
| 服务结果             |         通过 | 投递检查失败 | 测量窗口后被内存上限杀死 |

默认配置使用既有的 64/256 MiB Java 堆与 64 MiB 代码缓存设置。受限配置使用：

```text
-Xms64m -Xmx160m -XX:ReservedCodeCacheSize=96m
-XX:-UseJVMCICompiler -XX:+EnableJVMCI
-Dlibgraal.Xmx=128m -Dpolyglot.engine.CompilerThreads=1
--enable-native-access=ALL-UNNAMED
```

受限配置为 Java/Scala 保留 HotSpot 编译器，同时允许对客方 JavaScript 进行 Graal 编译。它通过了短暂的客户端投递检查，但随后的服务监控在 06:44:49 亚洲/上海 捕获到一次 OOM 杀死。因此检查器成功完成并不足以成为采用它的依据。

优化运行时确有其事：一份独立的诊断跟踪记录到 71 个已完成的优化事件，其中包括来自 `simulation.js` 的方法。确定性场景覆盖全部 16 名角色、12,800 个固定模拟步。Node、OpenJDK 与 GraalVM 产生了相同的检查点/事件摘要：

```text
e316a8c505dcfb71267ebcb5ae25fb8a71889312fc42d9d34c4ea298254e14b0
```

GraalVM 未被采用。在测试的工作负载中，它消耗了两倍以上的 CPU，内存余量不足，并且在受限配置下最终被服务内存上限杀死。更新工作量 p95 的小幅下降不足以抵消这些代价。该结果针对这台双 vCPU 主机上的这些配置；它不能证明所有 GraalVM 配置或更大的主机也会如此。关于运行时编译与引擎/源共享，参见 [GraalVM 嵌入文档](https://www.graalvm.org/latest/reference-manual/embed-languages/)；关于发行版与校验和，参见[官方下载页](https://www.graalvm.org/downloads/)。

## 冷启动调查

即使在移除 TCP 停顿之后，冷启动浏览器检查仍暴露出明显的首局 JVM 预热。一个原型在绑定 HTTP 之前，对整份角色阵容做确定性的隔离战斗预热。它在 21.3 秒内完成并保持在内存限制内，但它的首次 30 秒四客户端检查每客户端仅投递 751–884 个快照，服务端更新 p95 约为 15.6–16.2 ms。它未通过投递标准，并在选定发布定稿前被移除。该原型中的预热 API 或启动延迟都没有部署。

冷启动首局行为仍是一项局限。不要推断 TCP_NODELAY 修复了编译/调度停顿，也不要把 READY、回合切换与命中冻结的延迟与传输延迟混淆。后续工作应先隔离冷编译与调度器压力，再引入新的预热策略或改动运行时/内存预算。

## 验证

通过了 `npm run check`、`npm run check:backend`、`npm run package:server`（含 `npm run build`）与 `npm run build:pages`。Pages 构建在 `/mygo-fighter/` 下加载并游玩，没有失败资源响应或浏览器控制台错误。全部 279 个公网运行时媒体路径通过了清单、内容范围与缓存头检查。

两个隔离的公网浏览器上下文创建/加入了房间，选择角色、造成伤害、暂停/继续、刷新客机并恢复保留的会话。客机降到 110 HP，其会话在刷新后仍然存活。未观察到 JavaScript 页面异常或浏览器控制台错误。这些冷启动功能检查不作为干净的延迟基准呈现。

选定的生产发布在 60 秒主动预热后，由两个同时房间中的四个客户端通过公网 HTTPS/WSS 完成了 900.68 秒。检查器运行在阿里云主机上，并以正常证书校验访问公网主机名。因此它的 RTT 不作为开发机 WAN 路径的测量值。

每个客户端收到 53,900–53,940 个快照。没有意外断连、协议错误或服务重启。伤害、3v3 替补进度与事件 ID 匹配均通过：对端在 1v1 房间观察到 3,541 个匹配的唯一事件，在 3v3 房间观察到 3,328 个。平均后端 CPU 为 0.687 逻辑核，峰值服务内存为 290.5 MiB，服务端更新工作量 p95 为 2.45–2.87 ms。

所有四个验证会话随后都显式离开了房间。之后，来自开发机的一次独立 60.07 秒四客户端战斗测量也通过了，没有意外关闭或协议错误：

| 客户端观测的 WAN 指标                  | 早期原始设置对照 | 部署后的 `9207f12` |
| -------------------------------------- | ---------------: | -----------------: |
| RTT p50                                |     48.8–50.8 ms |         8.9–9.6 ms |
| RTT p95                                |     52.1–54.4 ms |       16.4–20.0 ms |
| 快照到达间隔 p95                       |     57.6–58.2 ms |       19.1–19.6 ms |
| 输入发送 → 在返回状态中观测到接收，p95 |     64.6–65.9 ms |       29.5–32.0 ms |
| 服务端更新工作量 p95                   |     2.34–2.41 ms |       3.64–3.75 ms |

早期对照使用交替移动，而部署后的运行使用战斗，并且发生得更晚。这些是观察到的运行结果，并不主张每一处差异都来自某一次代码改动。[早先的审计](DEPLOYMENT_PERFORMANCE_2026-10-26.md) 中先前那条同一连接的关/开/关实验，为移除约 40 ms 的传输停顿提供了更强的因果证据。

WAN 样本每客户端收到 3,674–3,676 个快照。它的会话也显式离开，释放了两个房间。冷启动测量与有意的游戏冻结不纳入任何关于预热后传输延迟改善的主张。

原始脚本、报告与编译器跟踪放在忽略的 `output/runtime-optimization/` 下；截图放在 `output/playwright/` 下。没有恢复任何已移除的测试套件。运行时对比单元是临时的；生产环境继续使用原有的 Java/服务内存配置。
