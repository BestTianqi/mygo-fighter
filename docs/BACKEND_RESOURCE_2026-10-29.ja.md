# バックエンドのリソース割り当て — 2026-10-29

ベースライン：`cc9a1dc`、プロトコル 24。Scala サービスは引き続き、ルームごとに同じ制限付きのプライベート GraalJS シミュレーションを実行します。今回の変更は、バンドル済みサーバーカーネルの一時的な割り当てを減らすもので、ルーム上限、戦闘のタイミング、ワイヤプロトコルは変えません。

## 変更点

- スナップショットのシリアライズは、オブジェクトの残余展開で Match インスタンスを列挙／コピーするのではなく、31 個のフィールドを直接構築します。フィールド一覧は `Snapshot` と照合して確認します。常設のチェックが、シリアライズされた各 Match 自身のフィールドと出力されたスナップショットを比較し、全キャラクター、2 人／3 人、一時停止、再開をカバーします。
- 入力処理はベースラインの実装のままです。入力再利用の実験は撤回されました。

## 分離 JVM での計測

これらのプローブは、インストール済みのポータブル JDK 21、アプリケーションの GraalJS クラスパス、プライベートコンテキスト、呼び出しスレッドの `ThreadMXBean.getThreadAllocatedBytes` を使います。ベンチマークは直列に実行し、並行するサービス負荷はありません。割り当て量は累積の一時的な割り当てであり、保持されたヒープや常駐メモリではありません。

| プローブ                                                       |     変更前 |     変更後 |
| -------------------------------------------------------------- | ---------: | ---------: |
| スナップショットのみ、12,000 パケット                          | 217.53 MiB | 179.99 MiB |
| スナップショット変更のみ、統合 6,000 ステップ / 3,000 パケット | 531.07 MiB | 523.03 MiB |
| 入力実験（撤回）、統合ウォームアップ平均                       | 531.19 MiB | 528.79 MiB |

分離したスナップショット経路の割り当ては 17.26% 減り、この JVM では 1 パケットあたり約 3,280 バイトを節約しています。スナップショットのみのウォームアップ経過時間は、変更前が 292/296/276 ms、変更後が 267/259/244 ms でした。統合時のスナップショット割り当ては 1.51% 減り、入力のみの統合割り当ては 0.45% 減りました。これらの個別の割合は合算しておらず、サービス全体の CPU やメモリ削減として提示するものでもありません。入力のタイミングにはウォームアップや順序の影響が出たため、CPU 改善の根拠には使っていません。入力の変更は出荷していません。

却下した代替案には、統合時の割り当てを増やした汎用キーループと、効果のなかった getter があります。再利用可能な可変スナップショットのエンベロープは型付きリテラルよりわずかに多く節約できただけだったため、より単純な実装を選んで破棄しました。

## 正しさの根拠

- スナップショット変換：全 16 キャラクターと 4 形式で、70,656 個の厳密なシリアライズ済みパケット／イベントチェックポイントを照合。実際の KO、控えの入場、結果、一時停止、再開、決着済みの試合を含みます。
- 常設の `check-server-snapshots.mjs` が `npm run check` の中で実行され、1,280 個の完全なスナップショット状態を検証します。
- 全体チェック、本番ビルド、バックエンドのコンパイル／フォーマット確認、Pages ビルドが通過しました。`/mygo-fighter/` で配信したページは、リソースを読み込み、ローカル戦闘に入り、移動・攻撃・一時停止をしてメニューに戻るまでエラーなく動作しました。

## サービス計測と選択

Windows、ポータブル JDK 21、インタープリト実行の GraalJS、`-Xms256m -Xmx2g`、ポート 8181。各比較では新しい JVM とループバックのクライアントを使い、既存の入場制限、2000 HP、時間無制限としました。スナップショットは 60 Hz のまま、シミュレーションは既存の周期のままです。他のベンチマークプロセスは停止しました。各ルームの 2 つの対端が毎秒 20 入力の頻度で移動と攻撃を交互に行い、対になる信頼性イベントの ID 列はすべて一致し、プロトコルエラーは発生しませんでした。

まず 1 ルーム、次に 8 ルームという試験で、2 つの最適化を同時に試しました（10/30 秒のウォームアップと戦闘、続いて一時停止／ロビーの段階）。8 ルームの戦闘区間では、平均 CPU が 1.101 -> 1.282 論理コア、最大ワーキングセットが 437.4 -> 507.1 MiB でした。分離計測の割り当ては減っていたものの、この結果は組み合わせ版の出荷を支持しませんでした。入力再利用の変更とその割り当て専用テストは撤回しました。

2 組目の比較では、新しい JVM を直接 8 ルームで起動し、20 秒のウォームアップ、20 秒の計測戦闘、続いて 5 秒の一時停止／ロビー段階としました。ベースラインと**スナップショットのリテラルのみ**（これが最終実装）を比較しています。

| 8 ルーム戦闘の指標                    | ベースライン | スナップショットのみの最終版 |
| ------------------------------------- | -----------: | ---------------------------: |
| 平均 CPU、論理コア                    |      1.23685 |                      1.16590 |
| 最大ワーキングセット                  |   449.73 MiB |                   454.54 MiB |
| サーバー更新処理 p95                  |    1.7908 ms |                    1.7722 ms |
| スナップショット到着間隔 p95          |   25.1590 ms |                   26.2999 ms |

この組ではアクティブ CPU が約 5.7% 減りました。常駐メモリは約 1.1% 増えたため、常駐メモリの削減は主張しません。このループバック実行では配信 p95 が約 1–1.6 ms 増えています。これはネットワーク遅延の改善を主張するものでも、容量を保証するものでもありません。短時間の実行では GC／ウォームアップや負荷のばらつきがこれらのサービス数値に影響します。より再現性の高い効果は分離した割り当て計測です。ハーネス冒頭の `empty` 段階にはルームのセットアップも含まれるため、アイドル計測として使ってはいけません。別途、後片付け後のベースラインを採取したところ、ルームが残っていない状態で 1 秒サンプリングにより 0 CPU が報告されました。

生のプローブ、JVM ログ、サービス計測は無視対象の `output/backend-reduce/` にあります。プローブが示すのは試験した負荷での挙動と割り当てであり、実際のサーバーの常駐メモリは GC、ランタイムのウォームアップ、ルームのワーキングセットの影響を受けます。
