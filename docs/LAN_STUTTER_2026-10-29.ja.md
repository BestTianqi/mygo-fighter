# LAN 戦闘のスタッタリング — 2026-10-29

2 人用 LAN 対戦で、両ピアのブラウザーに長時間の停止が再現しました。修正は、戦闘前にデコード済みのアートワークを利用可能に保ち、表示境界で古い権威スナップショットを統合し、共有カーネルから繰り返しのターゲット配列確保を除去します。キャラクターアート、アニメーション、エフェクト、入力バインディング、転送頻度、プロトコル 23 は維持されます。

## 根拠と変更

ベースラインは `cfb6700` でした。分離した Scala サーバーがポート 8082 で配信する本番ビルドで、1280 × 800、DPR 1.5 の Edge ブラウザーコンテキストを 2 つ動かしました。愛音と祥子が、地形有効、HP 2000、時間／エネルギー無制限、サウンドオフの条件で、繰り返し移動して J／K／U／O を使用しました。各条件は 6 秒のウォームアップと 12 秒の測定で、まずネイティブ速度、次に 4× CPU スロットリングを行いました。他の戦闘ベンチマークは同時に実行していません。

サーバー側の独立した 30 秒の 2 ピア WebSocket チェックでは、クライアントあたり毎秒約 57.8 スナップショットを配信し、最後の 10 秒間の更新は p95 2.30 ms、p99 2.94 ms でした。ブラウザーの計測により、長時間の停止はスプライトキャッシュの構築や通常のスナップショット再生ではなく、ネイティブの `drawImage` 内で発生していることが分かりました。スプライトキャッシュを迂回し、画像のシャドウを無効にしても停止は消えませんでした。デコード済みの `ImageBitmap` サーフェスを保持すると解消したため、エフェクトの削除やソース解像度の低下は不要でした。

- `CanvasRenderer` は戦闘準備中に画像をデコードし、保持ビットマップを作成します。ビットマップ作成が未対応または拒否された場合は、既存の HTML 画像にフォールバックします。2 件同時読み込みの制限は維持され、古く未使用の画像は既存の 384 MiB 目標に対して整理され、現在／控えに必要なアートは保護されます。エビクションと破棄は、破棄後に完了した読み込みも含めてビットマップリソースを閉じます。
- `PendingSimulationState` は、停止後に古いスナップショットを複製／再生する代わりに、次の表示フレーム用に最新の権威状態を保持します。信頼性のあるイベントは統合、重複除去、順序付けされ、既存の 2 秒の演出ウィンドウがバックグラウンドタブの保存量を制限します。epoch／世代、切断／ロビー／開始／破棄の境界は保留状態を消去します。到着タイムスタンプと確認／回線の診断はパケット受信時に留まり、古さの検出を維持します。権威的な HUD 値は予測とは別のままです。健全なクライアントはパケットの適用を次の表示フレームまで遅らせることができ、ローカル入力予測はフレームごとに継続します。
- `Match.targetSide` は 2 人モードで唯一の相手を直接選択し、3 人乱闘では確保／並べ替えを行わずにアクティブな相手を走査します。Node のマイクロベンチマークでは、48,000 ステップの中央値が 355.74 ms から 312.79 ms に、6,000 のフルシミュレーションフレームが 537.68 ms から 473.11 ms に短縮されました。これらはカーネルの測定値であり、ブラウザーの FPS や JVM スループットの主張ではありません。正確な状態／イベントの比較は、144,000 ステップ、5,776 のフル状態チェックポイント、24 のシード付き 2 人／3 人シナリオの全 16 キャラクターを対象にしました。

値はピア 0 / ピア 1 を示します。ロングタスクは 50 ms 以上のブラウザータスクで、測定ウィンドウ内でのみ集計します。

| ネイティブのロングタスク / 12 秒 | 21 / 16            | 0 / 0          |

どちらの条件でも、両クライアントはレンダースケール 2（1920 × 1080 のバッキングサーフェス）を維持しました。ベースラインはネイティブ速度でスケール 1 / 1.5 に、スロットリング下で 1 / 1 に低下していました。ページエラーは発生しませんでした。したがってこの改善は画質の低下に依存しません。ネイティブのローカル入力から可視の動きまでの p95 は、変更後が 7.5 / 8.3 ms、変更前が 26.4 / 8.4 ms でした。戦闘の凍結と合成された交互操作のため、これは分離したネットワーク遅延ベンチマークではなくスモーク測定です。

これは 1 回の制御されたローカルブラウザー試験であり、すべてのデバイスやキャンパスネットワークへの保証ではありません。ビットマップの保持は、繰り返しのデコード停止を避けるために安定したデコード済みワーキングセットを用意するトレードオフであり、メモリ削減を主張するものではありません。既存の画像予算と明示的な解放が古いアートの保持を制限し、選択したチームに必要なアートはその目標を超えることがあります。テストは WAN の RTT 改善や最大ルーム容量を測定していません。サウンド／動画のデコードや長時間セッションでのモバイル動作が依然として遅い場合は、別途測定が必要です。

## 検証

`npm run check`、`npm run build`、`npm run build:pages` が合格しました。`/mygo-fighter/` 配下で配信されたブラウザーは要求されたすべてのリソースを読み込み、ローカル戦闘に入り、移動、攻撃、一時停止、メニューへの復帰をページエラーなしで行いました。その 21 枚の canvas 画像は保持ビットマップでした。

3 つの実ブラウザーピアも、準備、3 人目の予測移動と権威的な入力確認、一時停止／再開、切断による一時停止、セッション復元と再開を通過しました。一撃 KO のテストルール下での実際の J 攻撃は、約 5 秒後に控えを出しました。3 つのピアは同じ 5 つの攻撃／ヒット／戦闘／KO／リスポーンイベントを重複なく提示し、ページエラーはありませんでした。このシナリオは 3 つの鏡像 `[0, 1, 2]` チームを使用し、保持された 26 枚の画像はクライアントあたり 204.43 MiB のデコード済みピクセルを表します。9 人の異なるキャラクターに対する測定ではありません。

生のスクリプトとレポートは Git 管理外の `output/lan-stutter/`、`output/brawl/`、`output/performance-kernel/` にあります。恒久的なチェックは、最新状態／イベント／ライフサイクルのセマンティクスとビットマップのフォールバック／解放を、既存の戦闘、3 人乱闘、プロトコルのチェックと並んで対象にします。更新後は、共有シミュレーションとクライアントが同じビルドを使うようにホストを再起動し、両方のブラウザーを再読み込みしてください。
