## 検証

`npm run check`、`npm run check:backend`、`npm run build:pages`、`npm run package:server`（`npm run build` を含む）が通過しました。Pages ビルドは `/mygo-fighter/` 配下で読み込まれ、練習モードに入れました。デプロイされた HTML は本番ビルドと一致し、334 個のメディアパスすべてとアセットのマニフェストがローカルの内容またはバイト範囲と一致しました。HTTPS 証明書の検証、HTTP から HTTPS へのリダイレクト、HTML の `no-cache`、メディアのイミュータブルキャッシュも通過しています。

公開プロトコル 22 の確認では、一時停止／再開、再接続、ホストのみの再開、無効なセッション、外部オリジンの拒否、旧プロトコルの拒否、ファイターのリセットが通過しました。隔離した 2 つのブラウザーで公開オンライン対戦を完走し、キーボード攻撃で防御側を 183 HP まで減らし、再読み込みしてもその状態が保持されて再開できました。どちらのブラウザーにもコンソールエラーはありませんでした。

オンラインの 8v8 確認では、全 16 キャラクターをカバーする 2 チームを編成しました。両方の対端が同じカスタムルールを受け取り、サーバーは 350 HP と初期エネルギー 80 を適用し、時間無制限でクロックを 90 秒に保ち、ゲストによるルール変更は拒否されました。満室と 5 番目のルームの拒否、2 分後の放棄セッションの失効、容量の回復、`Retry-After: 60` を伴う入場制限も通過しました。

認証済みの 4 クライアントが、公開 HTTPS/WSS 経由で同時進行の 1v1 と 3v3 において 900.00 秒を計測完了しました。それぞれ 52,116–52,154 個のスナップショットを受信し、ウィンドウ全体で毎秒 57.91 個以上、両方のルームでダメージがあり、3v3 では控えの進行もありました。予期しないソケット切断、プロトコルの不一致、バックエンドの自動再起動、メモリ上限イベントはありませんでした。サービスメモリのピークは 270.3 MiB でした。これらの測定にはウィンドウ前半の他の機能確認も含まれており、容量ベンチマークではありません。

**厳格な長時間テストのハーネスは、エラーなしの表明を満たしませんでした。** 1 つのクライアントが 20 秒の期限で非同期 HTTP 確認のタイムアウトを 1 回記録しました。ハーネスは、その要求が読み込みの確認かフィニッシュ演出の確認かを区別していません。記録されたクライアントエラーはこの 1 件だけで、両方の試合は継続しました。別の追試ではフィニッシュ確認の要求 60 件が成功しました（最大 42.1 ms）が、元のタイムアウトの原因は特定できませんでした。エラーチェックの後、ハーネスは以降のイベント対の表明をスキップしたため、この実行ではイベント ID の完全一致を主張しません。

ワークステーションのプロキシ DNS が、最初は使用できない合成アドレスを返しました。公開検証では、ホスト名、SNI、通常の証明書検証を保ったまま、サーバーの既知の IP へ向ける一時的なホスト名単位の DNS 上書きを使いました。システムの DNS 設定や証明書の検証は変更していません。

4 ルームの上限は[プロトコル 20 の容量監査](DEPLOYMENT_CAPACITY_2026-10-27.ja.md)から引き継いだものです。現在の確認は、8v8 やカスタムルールのすべての組み合わせで 4 ルームの容量があることを示すものではありません。コールド JVM 起動は引き続き制約で、起動ログには初回の試合読み込み中の CPU 飢餓の警告が含まれていました。
