## 意図した選択

- **1 つの成果物、3 つのサービスプロセス。** 公開 edge、ルームディレクトリ、ルーム実行は、独立してスケールし独立して障害になるため、`SERVICE_ROLE` で選択される別々のロールとして動作します。戦闘 tick ループは 1 つの rooms プロセス内に留まります。8.33 ms のループ内のネットワークホップはドメイン境界を改善せず、ルームの権威を曖昧にするからです。以前の単一 JVM はゲーム規模による判断であり、デプロイを結合し続ける理由ではありませんでした。
- **データベースはありません。** ルーム、入力、進行中の対戦は一時的なものです。入力パスにデータベースを置くと、満たすべき永続化要件がないのに作業だけが増えます。未使用の SQL テーブルやプレースホルダーの初期化子も追加していません。
- **`Connection` はアプリケーションリソースの接続です。** 要求される `plan(connection)` の形はそのままです。その `Connection` は未使用の JDBC 接続ではなく、生きたルーム/セッションのリソースと設定を含みます。
- **戦闘カーネルは共有の TypeScript です。** Scala がサーバーを所有し、埋め込みの制限付き GraalJS コンテキストで完全な戦闘カーネルを実行します。これによりキャラクター固有の仕組みを保ち、ローカル対戦と LAN 対戦を同じルールに保ちます。シミュレーション用の Node サーバーやサブプロセスはありません。
- **Canvas と Web Audio はエフェクトです。** これらは後始末を伴うページローカルのアダプターです。React はメニュー、選択、ダイアログ、読み込み/エラー状態、操作、HUD、ビデオのカットインを担当します。戦闘クロックは React のレンダリング外で動きます。
- **グローバルなフロントエンドストアは不要でした。** これは 1 つのまとまりのあるゲームページです。外部ランタイムスナップショットはページレベルのフックで消費します。無関係なグローバル状態の足場はありません。
- **インフラストラクチャオブジェクトはドメインオブジェクトと異なります。** セッション、ルーム、公開レスポンスのデータは不変のレコードです。Connection、Peer、RoomRuntime はエフェクトリソースを保持し、所有するインフラストラクチャ/ランタイムモジュールの下にあります。
