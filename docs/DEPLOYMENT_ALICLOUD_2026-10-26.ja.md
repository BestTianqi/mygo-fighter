## デプロイ構成

リリースは `/srv/mygo-fighter/releases/20261026-6d3d136-protocol10` にあります。`/srv/mygo-fighter/current` リンクが有効なリリースを選びます。そのリリースの `deployment.json` に、アプリケーションコミット、アーカイブのチェックサム、プロトコル、ホスティングサービスのチェックサムを記録しています。

実行時の設定は `/etc/mygo-fighter.env` にあります：

| 設定                | 値                              |
| ------------------- | ------------------------------- |
| `HOST`              | `127.0.0.1`                     |
| `PORT`              | `8080`                          |
| `WEB_ROOT`          | `/srv/mygo-fighter/current/web` |
| `MAX_ROOMS`         | `2`                             |
| `TRUST_LOCAL_PROXY` | `true`                          |

Caddy は公開 TCP 80/443 を提供し、HTTP を HTTPS にリダイレクトし、HTTP/WebSocket をループバックのバックエンドへ転送します。阿里云インスタンスのファイアウォールはこれらの公開 Web ポートをすでに許可していました。JVM は初期ヒープ 64 MiB、最大ヒープ 256 MiB、サービスのメモリ上限 512 MiB を使います。

初回利用時の検証で、GraalJS が制限されたサービスアカウントでは `/srv/mygo-fighter/.cache` を作成できないことが分かりました。サービスは現在 `CacheDirectory=mygo-fighter` と `XDG_CACHE_HOME=/var/cache/mygo-fighter` を使います。ネイティブ資源のキャッシュは書き込み可能で、アプリケーションのリリースとサービスのホームは読み取り専用のままです。この設定を適用した後、誤解を招く `truffleattach` 不足の警告は消えました。

## 運用と今後のデプロイ

```sh
ssh alicloud 'systemctl status mygo-fighter caddy --no-pager'
ssh alicloud 'sudo journalctl -u mygo-fighter -u caddy --no-pager -n 100'
curl --fail https://mygo-123-57-149-254.sslip.io/api/health
```

更新するときは、対応するディストリビューションをビルドし、アップロードしたアーカイブのチェックサムを比較し、新しいリリースIDで有効化します：

```sh
npm run check
npm run check:backend
npm run package:server
scp backend/target/universal/mygo-server-2.0.0.tgz alicloud:/tmp/mygo-server-2.0.0.tgz
ssh alicloud 'sha256sum /tmp/mygo-server-2.0.0.tgz'
ssh alicloud 'sudo bash /opt/mygo-fighter/activate.sh /tmp/mygo-server-2.0.0.tgz RELEASE_ID'
```

有効化とロールバックのスクリプトは `/opt/mygo-fighter/` に常設されています。今後の有効化が成功すると前のリリースが残り、`sudo bash /opt/mygo-fighter/rollback.sh` で戻せます。このホストへの初回のゲームインストールだったため、まだ戻せる前のアプリケーションリリースはありません。サービスを切り替えたり再起動したりすると一時的な対戦は終了します。
