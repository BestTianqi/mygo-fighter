# バックエンドのルーム拡張 — 2026-10-27

今回の更新は、1 試合あたりのサーバー処理を減らし、一時停止中とロビー中のクロック処理の大部分を取り除きます。Scala サーバー、ルームごとに制限された GraalJS コンテキスト、共有 TypeScript 戦闘ルール、すべてのアセット、プロトコル 15 は維持します。サーバーは引き続き、毎秒 100 の固定戦闘ステップと 60 のアクティブスナップショットを目標とします。

## 変更点

- アクティブなルームのスケジューリングは、単調増加の 120 Hz デッドラインを維持します。逃したデッドラインはスキップし、無制限のタイマー滞留として積み上げません。カーネルの追いつきは引き続き 50 ms が上限です。
- ロビー、一時停止中、完全に決着した試合は 250 ms のアイドル間隔を使います。境界付きの起床キューが、ルームや操作の変化でアイドルスリープを中断します。ビジー状態のルームロックはアクティブな周期で再試行し、操作の変化は次の状態公開を強制します。最後の KO／カウントダウンはスリープ前に最後まで実行します。
- アクティブな tick は通常のスリープを使い、tick ごとに新しく競合させる fiber のペアは使いません。起床キューと競合するのはアイドル待機だけです。
- 接続中の対端がいないルームはスナップショットのシリアライズを省略します。ロビーに戻るときはプライベートコンテキストを閉じ、各対端が保持している状態フレームを破棄します。既存の 2 分間の放置ルーム清掃と明示的な退出時の清掃はそのまま維持します。
- ルームは不変の WebSocket 状態／イベントフレームを 1 回だけ構築し、対端間で共有します。最新のみの状態、境界付きの信頼性イベント、ルームの所有権、再接続バリアはそのまま維持します。
- 各シミュレーションは、不変の Polyglot 呼び出しターゲットを 1 回だけ解決します。スキル解決は、スキルボタンが実際に押されたときだけそのフォームのスキルスキームを構築します。移動と通常攻撃のステップではこの割り当ては発生しません。
- クライアント予測は、一時停止／結果表示中の低いスナップショット周期を理解します。戦闘中は元の短い予測ホライズンをそのまま使い、決着済みの試合では外挿を止め、アイドル通信の欠落とソケット切断の検出は続けます。

## 同一マシンでの比較

ベースライン：アプリケーション `c184e45`。Windows、Intel Core Ultra 9 185H（16 コア / 22 論理プロセッサ）、Microsoft OpenJDK 21.0.12.1、インタープリト実行の GraalJS。どちらの実行も既存の開発用 JVM 設定（`-Xms256m -Xmx2g`）を使います。それぞれ分離ポート 8181 で新しいバックエンドを起動し、8 ルーム / 16 WebSocket クライアント、30 秒の戦闘ウォームアップ、30 秒の計測戦闘、10 秒の一時停止、続いて 10 秒のロビー滞在とします。クライアントは毎秒 20 入力の頻度で移動と攻撃を交互に行い、対端はまったく同じイベント ID 列を受け取ります。これは短時間のループバック負荷であり、インターネットや本番ホストの容量を保証するものではありません。

| 一時停止時の平均 CPU、論理コア                          |        0.668 |       0.078 |
| ロビー時の平均 CPU、論理コア                            |        0.375 |       0.147 |
| 10 秒間の一時停止スナップショット通信量、全クライアント | 27,260,286 B | 2,101,758 B |

観測された CPU の削減は、アクティブ約 20%、一時停止約 88%、ロビー約 61% でした。一時停止中のスナップショット通信量は約 92% 減っています。今回選択した実行では、プロセス全体のワーキングセットは**減少しておらず**、入力／スナップショット配信の p95 はむしろ高くなりました。これらの測定は、エンドツーエンドの遅延や常駐メモリが下がったことを示すものではありません。今回の変更が減らすのは CPU と一時的なメモリ割り当ての負荷であり、プロセスメモリと配信タイミングには GC、スケジューリング、負荷、ランタイムのウォームアップが引き続き影響します。サーバー更新時間の短縮がインターネットの ping 改善に等しいとは主張しません。

## 割り当ての測定

別に用意したシングルスレッドの JVM プローブで、同じキャラクターと入力、1 パスあたり 6,000 の固定ステップ / 3,000 のスナップショットを使って新旧のバンドル済みカーネルを実行します。各 JVM は新規に起動し `-Xms64m -Xmx256m` を使います。0 パス目でランタイムをウォームアップし、`ThreadMXBean.getThreadAllocatedBytes` で 1 パス目と 2 パス目を測ります。シリアライズ出力の文字数は一致しています。

| ウォームアップ周回 | ベースラインの経過時間 / 割り当て量 | 更新後の経過時間 / 割り当て量 |
| ------------------ | ----------------------------------: | ----------------------------: |
| 1                  |              957.44 ms / 506.77 MiB |        867.95 ms / 460.72 MiB |
| 2                  |              971.18 ms / 506.76 MiB |        861.33 ms / 460.70 MiB |

このカーネル負荷では一時的な割り当てが約 9% 減っています。割り当てバイト数は累積の割り当て量であり、生存中のヒープや節約された常駐メモリではありません。この数値はスキル解決の処理だけを切り出したもので、WebSocket の共有フレームやアイドルルームによる節約は含みません。

## 容量とライフサイクルの確認

さらに短い実行として、同時に 16 ルーム / 32 クライアントを使い、計測戦闘の窓は同じ 30 秒としました。57,844 個の戦闘スナップショットを受信し、プロトコルエラーはゼロ、16 ルームすべてでイベント ID も一致しました。戦闘時の更新処理 p95 は 1.96 ms、到着間隔 p95 は 28.56 ms、入力受信 p95 は 26.19 ms でした。戦闘時の平均 CPU は 3.54 論理コア、最大ワーキングセットは 493.2 MiB です。セットアップは既存の入場制限に従っており、制限を回避していません。このワークステーションでの結果は、2 vCPU/512 MiB の公開サービスで 16 ルームを検証するものではありません。

追加の確認も通過しました。

- ベースラインカーネルに対して、全 16 キャラクターで 17,600 個の厳密なシリアライズ済み状態／イベントチェックポイントを照合（一時停止／再開を含む）。
- 1v1 と 3v3 の最終 KO／カウントダウンを最後まで実行し、アイドル状態の結果表示と再開も確認。132 個の方向付きスキルケースと 88 個の 3 段コンボケース。
- 実 JVM の 3v3 で 3 人の控えをすべて打ち破り、最終結果が一致。20 回の一時停止／再開サイクル、ファイターを保持した再接続、無応答対端のタイムアウトも確認。この独立したローカルライフサイクル実行での一時停止公開 p95 は 45.6 ms、再開は 33.6 ms でした。
- 実際のブラウザクライアント 2 つで禁止／選択を完了し、3v3 に入り、誤った接続警告なしに一時停止して再開できました。
- `/mygo-fighter/` 配下の本番ビルドで、15 ステージすべてと移動が正常に動作し、ブラウザやリソースのエラーはありませんでした。
- `npm run check`、`npm run build`、`npm run check:backend`、`npm run build:pages`。

一時的な検証用スクリプト、生レポート、スクリーンショットは無視対象の `output/server-performance/` にあります。削除済みのテストディレクトリは復元していません。

## ロールアウトとルーム上限

スケジューリングとアイドル予測の両方の変更を反映するには、バックエンドを更新／再起動し、クライアントを再読み込みしてください。通常の LAN の既定値は `MAX_ROOMS=20` のままです。これは入場の上限であり、20 試合の同時対戦を約束するものではありません。設定上の上限を引き上げる前に、実際のホストで CPU 飽和とメモリを測定してください。これまで文書化した公開サービスは「2 ルーム/512 MiB」の明示的な予算を使っています。今回のコード変更は、それらのサービス、その制限、JVM 設定を変更もデプロイもしません。
