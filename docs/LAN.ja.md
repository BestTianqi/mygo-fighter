# LAN プロトコルとパフォーマンス

## タイミング

- 戦闘ルールは固定の **10 ms** ステップで進みます。
- 現在プレイ中の各ルームは、監視付きの **120 Hz** ループを 1 本所有し、単調増加の経過時間をカーネルへ渡します。ロビー、一時停止中、完全に決着したリザルトのルームは **4 Hz** で確認し、読み込み／再開／再起動では即座に起床します。最後の KO 演出はスリープ前に完了します。遅いルームがグローバルバッチを止めることはありません。ルームの削除はそのループに停止を通知し、アプリケーション終了時は残りのループをキャンセルします。期限切れのクリーンアップは別途 1 秒に 1 回実行します。停止したイテレーションの追い上げは最大 50 ms に抑え、無限の追い上げスパイラルを防ぎます。
- セットアップやコマンドが保持しているルームロックは、他のルームを止める代わりに、そのルームの今回のクロックイテレーションをスキップします。
- アクティブな権威スナップショットは **60 Hz** を目標とします。スケジューリングは端数の間隔を保持し、タイマードリフトを蓄積しません。一時停止中および決着済みの試合は **4 Hz** で配信し、制御／終局状態は即座に配信します。接続ピアがいないルームはスナップショットをシリアライズしません。
- ネイティブのキーボードとタッチのイベントは、1 本の永続 WebSocket で入力を即座に送信します。変化のない入力は 250 ms ごとに更新します。入力の変化は HTTP 応答を待ちません。
- ローカル予測は権威スナップショットを復元し、未確認の入力を同じ 2 人用カーネルで再生します。入力の受信と適用は別々に確認します。保留中のクイックタップはヒットフリーズ中も維持されます。入力履歴は 2 秒／600 件に制限し、枯渇時は権威から再同期します。
- 描画は `requestAnimationFrame` を使用し、通常の HUD 更新は 30 Hz に制限し、ライフサイクル更新は即座に行います。体力と勝敗は権威から取得します。小さな補正は 80 ms かけて視覚的に収束し、コリジョンボックスは動かしません。80 ワールド単位を超える補正、テレポート、KO、ライフサイクルの境界は即座にスナップします。
- アクティブな予測ホライズンは `clamp(smoothed RTT + 50 ms, 100 ms, 250 ms)` です。それを超えてアクティブスナップショットが欠けている場合は予測を凍結し、警告を表示します。一時停止中／決着済みの試合は外挿せず、スナップショット間が 1 秒空いてから古い状態の警告を表示します。ソケットのハートビートと再接続チェックは動作し続けます。一時停止、再起動、新しいラウンド、再接続は再生履歴を消去します。
- ピアごとに未送信の最新状態だけを保持します。各状態／イベントフレームは 1 回だけエンコードし、両ピア間でイミュータブルに共有します。ロビーへ戻ると保持中の状態フレームを消去します。制御メッセージは別の有界キューを使用します。クライアント側のソケットバッファーが大きくなると、入力遅延を蓄積せず再接続します。
- 入力パケットでは偽のボタンとゼロのカウンターを省略します。画像、音声、動画は別々に配信し、イミュータブルキャッシュを使います。試合前に読み込むのは選択されたバトルアトラスだけです。

TCP WebSocket は、ネットワークでパケットが失われると後続メッセージを遅延させることがあります。実際の LAN 遅延は Wi-Fi の競合、ホスト、デバイスの描画、ブラウザーのスケジューリングに依存します。

## ローカルランタイムキャッシュ

プロジェクトの Scala ランチャー（`node scripts/scala.mjs`。`npm start` と `npm run lan` も使用します）は、sbt の Ivy キャッシュを `output/toolchain/ivy/` に保存します。依存関係を Coursier 経由でダウンロードする場合でも、パッケージングは Ivy のロックを使用します。これにより、既定のキャッシュへのアクセスが拒否される Windows プロファイルで `failed to create lock file .../.ivy2/.sbt.ivy.lock` が発生するのを避けます。ランチャーは Git 管理外のプロジェクトディレクトリを自動で作成します。管理者権限もユーザープロファイルの変更も必要ありません。

`npm start`、`npm run lan`、`sbt run` は、Graal が展開するネイティブリソース用に書き込み可能なプロジェクトディレクトリ `output/polyglot-cache/` を使用します。これにより、`%LOCALAPPDATA%/org.graalvm.polyglot` の作成が拒否され、ランタイムが存在しない `truffleattach` リソースを誤って報告する Windows プロファイルを修正します。キャッシュは生成物で、Git 管理外であり、必要に応じて再作成されます。更新後はローカルバックエンドを再起動してください。警告を `polyglotimpl.AttachLibraryFailureAction=ignore` で抑え込まないでください。リソース展開の失敗を隠すだけです。[WAN.md](WAN.ja.md) に記載されている既存の公開サービス向けキャッシュ設定は別です。展開に成功しただけでは、JVM が最適化 JavaScript コンパイラーを提供していることの根拠にはなりません。

## HTTP 操作

公開の呼び出し元と Scala メッセージは、次の派生名を共有します：

| メッセージ         | POST エンドポイント | アイデンティティ                           |
| ------------------ | ------------------- | ------------------------------------------ |
| CreateRoomMessage  | `/api/createroom`   | セッションを作成                           |
| JoinRoomMessage    | `/api/joinroom`     | セッションを作成                           |
| ChooseRoomMessage  | `/api/chooseroom`   | 信頼済みセッション。ホストがステージを制御 |
| ReadyRoomMessage   | `/api/readyroom`    | 信頼済みセッション                         |
| LoadedRoomMessage  | `/api/loadedroom`   | 信頼済みセッション、世代、接続済みピア     |
| PauseRoomMessage   | `/api/pauseroom`    | 信頼済みセッション。再開には両ピアが必要   |
| RestartRoomMessage | `/api/restartroom`  | ホスト                                     |
| FinishRoomMessage  | `/api/finishroom`   | 信頼済みセッションと演出 tick              |
| LobbyRoomMessage   | `/api/lobbyroom`    | 信頼済みセッション                         |
| LeaveRoomMessage   | `/api/leaveroom`    | セッションを失効                           |

公開エッジはこれらの呼び出しを、そのルームコードを所有する rooms インスタンスへ転送します。ルームメッセージ自体は引き続き rooms プロセスで実行されます。`GET /api/health` はサーバーと各タイミング目標を識別し、edge／lobby／rooms の状態を報告します。HTTP ボディは 8 KiB に制限されます。クロスオリジンのブラウザーリクエストは拒否されます。トークンが WebSocket URL に現れることはありません。共有できるルームコードは `/ws?room=CODE` クエリとして現れます。[バックエンドサービス](SERVICES.ja.md)を参照してください。

## ソケットメッセージ

`/ws?room=CODE` に接続し、`{"type":"authenticate","token":"<six-hex-code>.<48 hex>","protocol":26}` を送信します。トークン内のコードとクエリのコードは同じルームを指している必要があります。両端は互換性のないバージョンを再読み込みのメッセージで拒否します。UI とサーバーは同時にデプロイしてください。認証はソケットを接続する前に信頼済みセッションを解決します。ソケットには認証まで 5 秒あります。以降の入力パケットは現在接続されているピアと照合されるため、置き換えられたソケットがプレイヤーを操作し続けることはできません。

クライアントメッセージは `authenticate`、`input`、`ping` です。サーバーメッセージは `room`、`prepare`、`state`、`events`、`pong`、`error` です。入力は単調増加の安全な整数 `seq` と `input` オブジェクトを持ちます。既知のアクション、真偽値の方向、上限付きの押下カウンターは Scala の境界で正規化されます。余分なアイデンティティ、体力、アクションのフィールドは効果を持ちません。

準備完了した両プレイヤーは、設定と世代を含む `prepare` メッセージを受け取ります。各 prepare メッセージは現在接続されている `peerId` も運びます。両者は画像の先読み後に、その世代と自分の peer ID を確認する必要があります。再接続後の再開も同様です。その後サーバーが権威試合を作成します。遅れて届いた読み込み確認が古い試合を開始することはできません。

state メッセージには `protocol`、ルームの `generation`、照合用の `epoch`、単調なシミュレーション `tick`、ミリ秒単位のサーバー単調 `time`、権威 `state`、決定論的再生に必要なラッチ済み `inputState` が含まれます。適用済み／受信済みのシーケンス番号と入力値は `inputState` にあり、トップレベルのフィールドとして重複しません。`inputTick` と違い、シミュレーション tick はヒットフリーズや準備／ラウンド遷移の間も進み、再起動でもリセットされません。epoch が変わると、同じ世代内のローカル予測履歴は無効になります。`serverUpdateMs` はスナップショットのシリアライズまでのルーム更新作業を測り、転送の配送は含みません。

演出イベントは `{id, at, event}` として、世代／epoch のメタデータを持つ独立した信頼性のある `events` バッチで運ばれます。RoomConnection はバッチをクライアント向けパケットに統合し、クライアントは各 epoch 内で重複を除き、2 秒より古いイベントをスキップします。停止後の TCP バックログも含みます。state は最新のみのままで、イベント履歴を重複して含みません。有界のイベントキューは溢れると演出の手がかりを黙って失う代わりに再接続します。カーネルは各 state／バッチを 1 回だけシリアライズし、Scala は再解析せずに転送メタデータを追加します。

## 障害時の動作

ソケットを閉じると入力が解放され、試合が一時停止します。サーバーは通信が 3 秒ないピアを切断済みと見なします。ブラウザーは、サーバーメッセージが 4 秒まったく届かない場合、または接続／認証中にサーバー通信が 6 秒ない場合に、独自に再接続します。閉じるハンドシェイクの失敗を待たず、古いソケットを即座に切り離します。再試行は 250 ms から 3 秒までバックオフします。健全なハートビート応答はアイドル状態のルームをつなぎ止めます。

再接続はピアを置き換え、その側の読み込み済みフラグを消去し、古いソケットがまだ閉じていなくても既存のシミュレーションを一時停止し、現在の設定を送信します。置き換えられたピアからの確認は、新しいピアの読み込みを完了できません。再開の確認は冪等で、新しい試合を決して作成しません。続行と再起動には、現在の両ピアが接続済みかつ読み込み済みである必要があります。それまでは UI が待機状態を表示し、続行を無効にします。両者が準備できると、プレイヤーは保持された試合を明示的に再開します。ブラウザーはタブ単位の session storage にセッションを保存するため、再読み込みで再接続できます。明示的な退出はそれを削除し、保留中の準備／再試行処理をキャンセルします。遅れて届いた HTTP エラーが放棄したロビーを再び開くことはできません。

プロトコル 4 は現在のピアに対する読み込みバリアを追加します。更新後、ホストはバックエンドを再起動し、両方のブラウザーを再読み込みする必要があります。互換性のないクライアント／サーバー（古いバックエンドのバージョンエラーを含む）は、再開準備について黙って食い違う代わりに、その指示を表示します。

プロトコル 5 はヴィオラを 15 番目のキャラクターとして追加し、ロスターを 16 キャラクターに拡張します。ルームの選択、チームの検証、共有シミュレーションのすべてが彼女を受け入れます。古いクライアントは彼女の技定義とアートワークを持たないため、バージョンチェックが混在インストールを試合前に拒否します。更新後はホストを再起動し、両方のクライアントを再読み込みしてください。

プロトコル 6 は立希の改訂されたドラムキットを運びます。`rikiEightBoost` と 4 段パルスの必殺技タイミングを含みます。古いクライアントはこの強化攻撃を再生できず、ダメージも正しく予測できません。ホストと両方のブラウザーを一緒に更新してください。

プロトコル 7 は楽奈の 2 段のキャットステップ、改訂されたパフェの軌道、より安価な 4 音ソロ、より速い 3 段の必殺技を運びます。古いクライアントは異なるタイミングと飛び道具の軌道を予測します。更新後はホストを再起動し、両方のブラウザーを再読み込みしてください。

プロトコル 8 はサーバーが管理する BAN／ピックのロビーを追加します。通常の 1v1／3v3 では `RoomView.draft` は null で、それ以外では `bans`、`phase`（`ban`、`pick`、`complete`）、`turn`（0、1、または null）を含みます。ホストは `ChooseRoomMessage` の `format: "3v3", draft: true` フィールドで有効にします。両チームはクリアされ、1P が 1 回、2P が 1 回 BAN した後、交互に 6 回ピックします。BAN は両プレイヤーに適用され、ピックされたキャラクターは両チーム間で排他的です。各 `ban`／`pick` コマンドは 1 つのキャラクター ID だけを含み、チームやルーム設定を同時に変更することはできません。サーバーはルームロックの下で現在の手番、ステージ、両方の接続、キャラクター ID、可用性を検証します。通常モードは従来どおり鏡像の対戦ラインアップを保ちます。

BAN／ピックの完了が準備完了と既存の読み込みバリアの前提となり、順序付きのチームが変更されていない 3v3 リレーカーネルへ入ります。ソケットの置き換えやブラウザーの再読み込みでもドラフトは保持されます。明示的な選び直し、プレイヤーの明示的な退出、ホストの **重新禁选** 操作は最初からやり直します。マップ／地形の変更は BAN とピックを保持しますが、準備完了は解除します。モード、共有ルールの変更やドラフトのリセットができるのはホストだけです。ローカルの音声設定は独立しており、ネットワーク対戦に入っても保持されます。ロビーとローカル選択は同じ正方形のキャラクターカード、キャラクター／フォームのプレビュー、順序付きのチーム枠を共有します。確認操作により、誤クリックで BAN が確定することはありません。

プロトコル 9 は同期したキャラクター入場を追加します。既存の準備完了フェーズは 2750 ms 続きます。2100 ms のキャラクター固有の演出に続き、650 ms の READY です。`entrySides` は `phaseMs` とともにシリアライズされ、レンダラーはローカルイベントを再生する代わりにこの共有クロックからポーズ、移動、エフェクトを導きます。一時停止はそれを凍結し、置き換えられたソケットは現在の進行から再開します。3v3 の生存者は HP／共鳴を保持して入場を省略し、新しく出た控えだけが演じます。実際のファイター座標、リソース値、攻撃／やられ判定の状態は戦闘開始まで変わりません。視差効果を減らす設定のレンダラーは静的ポーズとラベルを表示します。更新後はホストと両方のブラウザーを一緒に再起動し、再読み込みしてください。

プロトコル 10 は共有コマンドリゾルバーを通して Mujica と MewType の立ち J コンボを復元します。J の連打は現在のキャラクター／フォームに応じて既存の起手、Jab2、Jab3 を選び、タッチの連打も同じ経路を使います。MyGO と Penguin は既存の 3 段マッピングを保ちます。硬直、ダメージ、共鳴、しゃがみ／空中の通常攻撃、K の強攻撃は既定のルールを維持します。クライアントとホストは一緒に更新し、予測が同じ攻撃名に従うようにしてください。

プロトコル 11 は、信頼性のある演出イベントバッチと最新のみの状態スナップショットを分離します。`events` フレームは世代／epoch のメタデータを含み、RoomConnection によってクライアント向けパケットに統合されます。確認とラッチされた制御入力は `inputState` にあります。[パフォーマンスの記録](PERFORMANCE.ja.md)を参照してください。

プロトコル 12 は改訂された 2 段地形と統一された通常攻撃判定を導入し、プロトコル 11 の転送方式を維持します。J の 3 段としゃがみ／空中の通常攻撃は 200 の前方リーチと 240 の高さ許容を共有します。K はその寸法の 1.2 倍を使います。Mujica 形態の通常攻撃は現在の J／K 寸法を 1.1 倍します。すべてのマップに高さ 144／288 の長いプラットフォームと、両側から徒歩で到達できる地面のテラスがあります。ステージのソース、ブラウザーのマニフェスト、サーバーの地形は一致しています。更新後は再ビルドしたホストを再起動し、両方のクライアントを再読み込みしてください。

ロビーへ戻ると古いシミュレーションコンテキストが閉じられ、世代が進みます。ルームエラーはそのルームをロビーへ戻します。空のルームは退出時に削除され、非アクティブなルームとそのセッションは 30 分で失効します。シャットダウンはすべてのシミュレーションコンテキストを閉じます。

既定の LAN デプロイは平文 HTTP を使用します。公開デプロイは同一オリジンの HTTPS プロキシと、[WAN ホスティング](WAN.ja.md)に記載された制限を使用します。どちらのデプロイもアカウントではなく一時的なルームセッションを使います。接続ピアのいないルームは 2 分で失効し、その間の再接続は既存セッションを復元します。既存の 30 分の非アクティブ失効も適用されます。

## 診断と検証

ゲームの URL に `?diagnostics=1` を付けると、ローリング p95 フレーム時間、補正距離、スナップショットの間隔／バイト数、サーバー更新時間、入力からシミュレーションステップまでの遅延、入力から可視の動きまでの遅延が表示されます。同じサンプルは `window.mygoDiagnostics` としても公開され、ブラウザーから検査できます。診断は既定でオフです。動きのサンプルには正当な攻撃硬直、阻害、ヒットフリーズが含まれることがあります。以前のブラウザー受け入れチェックは、戦闘前の妨害のない移動を別途測定していました。

LAN プロトコルを変更する前に、`npm run check`、`npm run build`、`npm run check:backend` を実行してください。Scala サーバーを起動した状態で、2 つのクライアントがルームを作成／参加し、チームを選択し、読み込みバリアを完了し、移動、一時停止、再起動、再接続できることを確認します。プレイ中は `?diagnostics=1` でフレームのタイミングと補正を確認します。以前の自動テストスイートは削除されました。ローカルの検証成果物は Git 管理外の `output/` ディレクトリに保存してください。

以下は以前の回帰ハーネスによる過去の測定値です。決定論的な予測トレースは、同じ入力とネットワークタイミングで古い上書きアルゴリズムと照合機構を比較するもので、2 回目のフルビルドベンチマークではありません。実サーバーの `baseline` レポートはこれらの変更前に取得したものです。Apple M4 Pro（14 コア）では、ジッターを注入した状態でも 4 ルームの p95 スナップショット配送間隔は約 24 ms のままで、1 ルームと同程度でした。p95 サーバー更新作業は約 1.0–1.1 ms でした。照合機構は 3 つの合成トレースすべてで最大補正距離を減らしました。p95 補正距離は 80 ms で改善し、20／150 ms では実質的に変わりませんでした。イベントと再生メタデータを保持することで、典型的な戦闘スナップショットは約 2.8 KB から 5.1 KB に増えました。これは演出の手がかりの復元のために意図的に帯域を犠牲にするものであり、帯域削減の主張でも、より遅いホストへの保証でもありません。

## 3v3 リレー

ホストはロビーで `format`（`1v1` または `3v3`）を選択します。各プレイヤーは ChooseRoomMessage で順序付きの `team` 配列を送信します。チームは重複しないキャラクター ID（0–15）を含み、準備完了前に 1 名または 3 名が必要です。不完全なチームは編集できますが、準備完了にはできません。選択やルールの変更は両者の準備完了フラグを解除し、世代を進めます。形式、アリーナ、地形を変更できるのはホストだけです。

prepare 設定には両チームと形式が含まれ、クライアントは 6 名のファイターとその形態をすべて先読みします。共有サーバーのシミュレーションは、フィニッシュ演出の後に敗北した側を進め、生存ファイターの HP とエネルギーを保持し、片方のチームが尽きたときだけ終了します。スナップショットはチームインデックス、控え、現在のファイターを運びます。再起動は両チームをリセットし、ロビーへ戻ると選択は編集用に保持され、準備完了は解除されます。再接続は既存の権威試合とそのチーム進行を復元します。

リレー関連の変更をレビューするときは、同じサーバーに対して 2 つのブラウザーを使い、ホスト専用ルール、順序付きチーム、準備完了、生存者の HP／エネルギー引き継ぎ、試合完了、再接続の復元を確認してください。

## 再接続の修正検証 — 2026-10-25

今回の更新は、編集前に 2 つの不具合を再現しました。受信トラフィックのないソケットが再接続に入らないこと、そして置き換え後のブラウザーがアセットを確認していないのにサーバーが続行を受け入れたことです。検証は 8 つの決定論的なクライアントライフサイクルケース、実際の KO と控えファイターを含む実サーバーの 3v3 試合、早すぎる続行と古いピアの確認の拒否、冪等な再開確認、保持されたチーム／HP／共鳴を対象にしました。分離した 2 つの実ブラウザーで、移動、一時停止／再起動、受信メッセージの遮断、自動再接続、再読み込み、ロビーへの復帰も確認しました。遅延させた読み込みリクエストで、表示される待機メッセージと無効化された続行ボタンを検証しました。一時ハーネスとスクリーンショットはその後クリーンアップしました。フロントエンド／アセット／ビルドと Scala のコンパイル／フォーマットのチェックは引き続き必要です。今後の一時的な検証出力は Git 管理外の `output/` ディレクトリに保存してください。

## 奥義フィニッシュと控えのエネルギー、プロトコル 16

致命的な必殺技は、その攻撃、所有者、フォームを共有シミュレーションに記録します。RoundEnd は既存の 3200 ms のリザルトシーケンスのためにその同一性を凍結します。通常の KO、引き分け、時間切れの結果は奥義フィニッシュを発生させません。700 ms の時点で、信頼性のある ultimateFinish イベントが立ち絵のカットイン、キャラクターカラーのバースト、原作の必殺技ボイスとともに 1 回発生します。すでに再生中のセリフは最初からではなく続行されます。一時停止は共有の演出クロックを凍結し、再接続は消費済みの手がかりを再生し直さずにアート状態を復元します。予測は生存ファイターのスナップショットを復元するときに任意の致命的メタデータを消去します。

3v3 では、各チームの 2 番目と 3 番目の出場者が共鳴 30 で開始します。生存したファイターは実際の HP と共鳴を保持します。最初の出場者と試合全体の再起動は以前の開始ルールを維持します。ホストを更新・再起動し、両方のクライアントを一緒に再読み込みしてください。プロトコル 16 は古い戦闘ルールを拒否します。
