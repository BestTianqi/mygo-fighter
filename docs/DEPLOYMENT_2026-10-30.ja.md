## 主要な問題と選択した変更

1. **初期の lobby 予算では安定して起動できませんでした。** 提案していた 128 MiB の cgroup 制限では、Linux が起動中に新しい lobby を kill しました。本番の制限は 192 MiB になりました。edge も観測されたワーキングセットに基づき、192 MiB ではなく 256 MiB を受け取ります。これらの制限は JVM のネイティブメモリを含み、変更されていない 48/80 MiB の最大 Java ヒープとは別のものです。
2. **4 つのアクティブルームが 2 vCPU のホストを過負荷にしました。** 45 秒のウォームアップ後の 60 秒間の 4 ルーム試験は、クライアントをサーバー上でループバック経由で動かしても失敗しました。最小配信 12.46 Hz、最悪配信間隔 p95 293.45 ms、更新処理 p95 19.31 ms、ping 応答の遅延です。測定したロール CPU は合計 1.76 論理コアでした。負荷クライアントと OS がさらに CPU を使いました。`vmstat` はアイドル時間ゼロを示しました。診断サンプルには cgroup の CPU クォータ、メモリ制限イベント、ハイパーバイザーの steal はありませんでした。以前のトンネルベースの試験も失敗しましたが、ループバックでの実行により、この過負荷の再現にインターネット経路は必要ないことが確立されました。
3. **コールド初期化が通常のプロキシタイムアウトを超えました。** 最後の `loadedroom` の確認応答が GraalJS コンテキストを作成します。以前の 10 秒のプロキシ制限は、その後にルームが戦闘に入った場合でも HTTP 504 を返しました。現在、この操作だけが上流で少なくとも 60 秒、ブラウザーで 65 秒を受け取ります。他の API は既存のタイムアウトを維持します。これは偽の失敗を修正するものであり、初期化コストを排除すると主張するものではありません。
4. **コールド JVM の処理とガベージコレクションが一時停止を引き起こしました。** ルーム JVM のログには、メタデータとコードキャッシュのしきい値による full GC が記録され、100 ms を超える一時停止も含まれていました。ルームは 64 MiB ではなく 128 MiB のヒープで起動し、64 MiB ではなく 128 MiB のコンパイラーキャッシュを確保しますが、256 MiB のヒープ上限と 512 MiB の cgroup 制限は維持します。すべてのロールは 96 MiB の初期メタデータ GC しきい値を使います。これはメタデータのメモリ上限でも、事前に割り当てられた 96 MiB のバッファーでもありません。起動は各ロールのヘルスを待ってから次のロールを起動するようになり、3 つのコールド JVM が同時に立ち上がることを避けます。
5. **レガシー復旧が新しいサービスレイアウトと互換性がありませんでした。** 有効化とロールバックは、保持されている単一ユニットリリースを認識し、競合するユニットを停止し、必要に応じてその `mygo-fighter` ユニットを復元し、正しい起動時有効化を復元するようになりました。`install.sh --prepare-only` は新しいユニットを準備しながら古い公開サービスを利用可能に保ちます。レガシーのロールバック対象を保持している間は、無効化されたレガシーユニットと `/etc/mygo-fighter.env` を保持してください。

選択した構成は rooms インスタンス 1 つと 2 ルーム上限を使います。rooms JVM をもう 1 つ追加すると、このホストの限られたメモリをさらに消費し、CPU 容量は増えません。3 ルームはスクリーニングしていないため、2 は選択した品質予算であり、証明された最大値ではありません。有料のリソース増強、ケイデンスの引き下げ、戦闘ルールの変更、メディアの削除、GraalVM ランタイムへの移行は行っていません。

## 制御されたゲームプレイ測定

すべての負荷は直列に実行しました。現在のカーネルは一定に保ちました。クライアントは 20 Hz で統一された移動／アクション入力を送り、地形有効、2,000 HP、無限の時間／エネルギー、通常のクールダウンで、3 キャラクターのチーム戦を 2 人のピアが共有しました。JVM チューニングとルーム数の変更は一緒に評価しているため、個々の CPU 効果は分離されていません。

## 公開ゲームプレイのソーク

5 つのクライアントが 18.76 秒の準備と 45 秒のウォームアップの後に、300.01 測定秒を完了しました。負荷は 8v8 のチーム戦と 3 人対戦を同時に実行し、地形有効、350 HP、無限の時間／エネルギー、標準クールダウン、交互の移動／攻撃でした。5 つのクライアントはすべてダメージとリザーブ進行を受け取りました。チーム戦の 2 つのピアは同じ 1,266 個の信頼できるイベント ID を、3 人対戦のピアは同じ 2,017 個の ID を受け取りました。予期しないクローズ、プロトコル／API エラー、自動再起動、メモリ制限イベントはありませんでした。サンプリングしたロールメモリは合計で最大 638.38 MiB、ロール CPU は平均 1.37 論理コアでした。最小配信は 53.89 スナップショット／クライアント／秒、最悪間隔 p95 は 40.34 ms、最悪サーバー更新 p95 は 16.38 ms でした。配信と整合性のゲートに合格しました。ウィンドウ前半のブラウザー受け入れも、これらのサービス負荷の数値に含まれます。

ネットワークレイテンシーは依然として明確に悪いままでした。最悪 ping p95 は 738.33 ms、戦闘入力から適用まで p95 は 775.07 ms でした。これらの結果を低レイテンシーのゲームプレイと表現してはいけません。クライアントのルックアップはホスト名を `198.18.0.196` に解決しました。これはクライアントのルーティング経路上にあるローカルの合成アドレスです。通常の HTTPS ヘルスリクエストは 1.034 s かかりましたが、同じホスト名の HTTPS リクエストを実際のサーバーアドレス `123.57.149.254` に固定し、通常の TLS 検証で行うと 55.82 ms でした。これはクライアントの経路が追加の遅延源であることを示します。以下のプロセス単位の直結ルート比較は、システムの DNS、VPN 設定、その他の接続を変更しません。

これは有限のゲームプレイ負荷であり、すべてのカスタムルールの組み合わせを網羅するものではありません。コールドの初回コンパイルと時折の長いテールの更新停止は残ります。初期化タイムアウトを広げてもそれらは解消されません。

## 直結ルートの比較

続くウォームアップ済みの 5 クライアント実行は、15 秒のウォームアップの後に同じ混合形式を 120.03 測定秒繰り返しました。この検証プロセスだけがホスト名の DNS ルックアップを `123.57.149.254` に固定しました。HTTPS/WSS のホスト名、証明書検証、サーバーリリース、ゲームプレイのケイデンスは変わりません。サーバーのソケット検査はクライアントの直結経路を確認しました。

- 最小配信：57.71 スナップショット／クライアント／秒。
- 最悪スナップショット間隔 p95：28.91 ms、最悪サーバー更新 p95：10.60 ms。
- 最悪 ping RTT p95：74.29 ms、最悪戦闘入力から適用まで p95：122.13 ms。
- ロール CPU 平均：1.30 論理コア、サンプリングしたロールメモリ合計の最大：646.62 MiB。
- 両方のルームでイベント集合が一致し、予期しない切断やクライアントエラーは発生しませんでした。

これは後続のウォームアップ済み実行であり、ランダム化した前後比較実験ではありません。独立したペアの HTTPS プローブが、バックエンドのコード変更と混同せずにルーティングの差を確立します。上の公開 5 分間の実行には、依然としてクライアントの通常のルーティング経路とその高いレイテンシーが含まれています。

公開モバイルブラウザーの受け入れも、デプロイ済みのゲームを読み込み、ローカル戦闘に入り、縦向きと横向きの円形コントロールをコンソールエラーなしで検証しました。Pages ビルドは `/mygo-fighter/` の下でコンソールエラーなしに読み込まれました。

生のログ、一時的な検証スクリプト、レポート、スクリーンショットは、無視される `output/deploy-20261030/` の下にのみ保管されています。一時的なサーバー側のベンチマークプロセスとランタイムは検証後に削除されます。インストールされた本番サービスは Java だけを必要とします。
