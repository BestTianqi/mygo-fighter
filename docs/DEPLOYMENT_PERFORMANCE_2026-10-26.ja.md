## 検証と測定方法

`npm run check`、`npm run check:backend`、`npm run package:server`（`npm run build` を含む）、`npm run build:pages` が通りました。Pages ビルドは `/mygo-fighter/` の下で開き、メニューと画像は失敗したリソース応答なしで読み込まれました。公開ヘルスチェックは `mygo-scala`、120 Hz シミュレーション、60 Hz スナップショットを報告しています。279 個の公開ランタイムメディアパスはすべて、現在のローカルマニフェストに対して内容とキャッシュヘッダーのチェックに合格しました。

2 つの分離された実ブラウザーコンテキストで、ルームの作成／参加、キャラクター選択、ゲームプレイ／ダメージ、一時停止／再開、更新／再接続を試しました。ゲストのヘルスは 128 に達し、更新後もセッションが保持されました。JavaScript のページ例外は発生していません。意図的なセッションクリーンアップ中にブラウザーのトランスポートコンソールエラーが 1 件発生しましたが、原因不明のゲームプレイ切断ではありません。

以前のリリースは、同時に動く 1v1 ルームと 3v3 ルームで 4 つの公開 WebSocket クライアントを使って 120 秒間測定しました。新しいリリースは同じクライアント負荷を使います。これらのクライアントはブラウザーレンダリングのコストなしで権威状態とトランスポートを検証します。レンダリングは Apple M4 Pro のハードウェアアクセラレーション Chrome で、DPR 1、バッキング解像度 960 × 540、バージョンごとに約 18 秒で別途測定しました。

生の測定値、スクリプト、パケットサマリー、スクリーンショット、JVM 録画は、無視される `output/deployment-performance/` と `output/playwright/` に保管されています。テストスイートは復元していません。

### 重要な制限

以前の 120 秒の実行は、前半の後にアーカイブのアップロードと重なりました。新しい長時間の実行には、コールドルームのウォームアップ、30 秒の JFR プロファイル、一時的な 5 秒のソケット実験が含まれます。プロファイリング区間は大きな CPU 競合と数秒級の外れ値と重なったため、その集計のテールレイテンシーはクリーンなリリース比較ではありません。別の、ウォームアップ済みでプロファイルしていないソケット比較が、通常のタイミングと提案されたトランスポート設定を測定します。

新しいコミットは戦闘範囲と地形も変更しています。パケットサイズと処理の差をトランスポート最適化だけに帰属させることはできません。READY、ラウンド遷移、ヒットフリーズにまたがる入力から適用までのサンプルには意図的なゲームの一時停止が含まれ、生のネットワークレイテンシーではありません。クライアントが観測する確認応答は往復とスナップショットのスケジューリングを含み、片道のタイミング測定ではありません。

## 測定で確立できたこと

このマシンではローカルレンダリングはすでに 60 fps に近く、そのまま維持されました。フレーム p95 は 16.8 ms から 16.7 ms に変わり、どちらのサンプルでもロングタスクは 0 でした。JavaScript コールバック p95 は変更前 0.6 ms、変更後 0.7 ms でした。このハードウェアサンプルはレンダリング速度の大きな改善を立証するものではありません。[以前のパフォーマンスレポート](PERFORMANCE.ja.md) の制約されたデバイスでの測定は別の負荷を扱っています。

以前の 4 クライアント負荷は、state パケット p95 が 5,841–6,157 バイト、サーバー更新 p95 が 4.10–5.36 ms、クライアント RTT p95 が 62.7–64.5 ms でした。初期の競合の少ないサンプルでは RTT p95 は約 52–53 ms でした。新しい戦闘の実行は state パケット p95 が 4,007–4,127 バイトで、約 31–33% 小さくなりました。RTT の中央値は依然として 50 ms 付近でした。パケットが小さいだけでは、以下のトランスポートの停止は解消されません。

## 主要な問題と次の最適化

### 1. バックエンドの TCP バッファリングが回避可能なレイテンシーを加える

稼働中の JVM が受け入れた TCP ソケットは `TCP_NODELAY=0` でした。ループバックでのパケットトレースでは、WebSocket ヘッダーがそのペイロードと別に送信され、一部のペイロードは約 40 ms 保持されていました。この遅延は Scala バックエンドと Caddy の間に存在し、公開ネットワーク配信の前です。低い `serverUpdateMs` には含まれません。

範囲を限定した実験で、アクティブな検証接続を 1 つだけ 5 秒間変更し、その後で元のオプションに戻しました。

| ヘッダーからペイロードまでの遅延 | 元のソケット | 一時的な TCP_NODELAY |
| -------------------------------- | -----------: | -------------------: |
| サンプル数                       |          169 |                  307 |
| p50                              |     0.781 ms |             0.136 ms |
| p95                              |    40.956 ms |             0.560 ms |
| 最大                             |    41.907 ms |             4.008 ms |
| 30 ms を超えたサンプル数         |           31 |                    0 |

最優先のコード変更は、`backend/src/main/scala/services/system/api/Main.scala` で `EmberServerBuilder.withAdditionalSocketOptions` を通じて `SocketOption.noDelay(true)` を設定することです。デプロイされたアプリケーションは取得したコミットのままで、診断用のオプション変更は一時的であり、テスト接続が閉じる前に戻されます。固定された [http4s 0.23.32 のビルダー](https://github.com/http4s/http4s/blob/v0.23.32/ember-server/shared/src/main/scala/org/http4s/ember/server/EmberServerBuilder.scala) はこのオプションを公開し、それ以外では追加オプションを空のリストに既定します。

このヘッダー／ペイロードの結果自体はエンドツーエンドのゲームプレイレイテンシーの結果ではありません。以下の独立したオフ／オン／オフの実験が、クライアントが観測するタイミングを検証します。

### 2. GraalJS がインタープリターフォールバックで動作している

デプロイ済みの jar とランタイムを使った単独のプローブは `Polyglot implementation: Interpreted` を報告しました。その警告は JVMCI が無効であることを示しています。JVMCI を有効にした 2 回目の単独プローブも `Interpreted` を報告しました。Libgraal／必要なコンパイラーが利用できないためです。本番の警告抑制フラグは警告を隠しますが、最適化を有効にはしません。

30 秒の JVM 録画では、サンプリングした 2,100 個の実行スタックのうち 1,584 個（75.4%）が GraalJS/Truffle に関係し、359 個（17.1%）が Truffle フレームなしの Cats Effect に関係していました。これらはサンプリングしたスタックのカテゴリーであり、完全なウォールタイムの割合でも、個々の戦闘関数への正確な CPU 配分でもありません。スタックは切り詰められているため、シミュレーションとシリアライゼーションの正確な内訳は得られません。

ヤング GC の一時停止が 33 回、合計 127.8 ms あり、最大は 12.75 ms でした。64 MiB のコードキャッシュには余裕が残り、コンパイルは有効でした。この証拠は、単にヒープやコードキャッシュを拡大するよりも、ランタイムの実行とスケジューリングを優先すべきことを示しています。

互換性のある最適化 GraalVM ランタイムを別の環境でベンチマークしてください。コールドスタートのコスト、定常 CPU、ネイティブメモリ、既存の 512 MiB のサービス上限を含めます。共有 TypeScript カーネルとルームごとの分離コンテキストは維持します。また、システム所有の `Engine` とキャッシュされた `Source` をコンテキスト間で再利用すること、対戦を受け入れる前に代表的なカーネルをウォームアップすることを評価してください。[GraalVM の埋め込みドキュメント](https://www.graalvm.org/jdk24/reference-manual/embed-languages/) がランタイムコンパイルの要件を説明しています。この監査では Java ランタイムも本番 JVM フラグも変更していません。

### 3. 大きなプロトコル変更の前にキューイングと割り当てを測定する

`serverUpdateMs` はルーム tick で始まり、最後のソケット書き込みの前に終わります。すべてのタイマーの遅れ、コマンドロックの待機、クライアントの到着を表すものではありません。スケジュールされた tick の遅れ、ルームロックの待機、カーネルの前進、スナップショットのシリアライゼーション、ソケットのフラッシュについて個別の測定を追加してください。入力の応答性を評価するときは、確認応答の指標をエポックとアクティブな戦闘の範囲に限定してください。

TCP の停止を取り除きランタイムを検証した後、60 Hz の完全な JSON スナップショットが依然として CPU、割り当て、または外向き帯域を支配しているかを測定してください。定期的な完全復旧スナップショットを伴うコンパクトなスナップショット／デルタ形式が次の一手になり得ます。generation／エポックのチェック、最新のみの状態、信頼できるイベント、権威ある入力カウンターは維持してください。レイテンシーのトレードオフを測定せずにスナップショット頻度を下げたり、アーキテクチャを書き換えたりしないでください。

## 最終的な安定性とソケット比較

新しいリリースは、同時に動く 2 つのルームで 4 クライアントを使い、900.03 秒を完走しました。各クライアントは 49,847–50,083 個のスナップショットを受け取り、予期しないソケットクローズやプロトコルエラーはありませんでした。ダメージ、リザーブ進行、一致するイベント ID は合格しました。ピアは 1v1 ルームで 3,188 個、3v3 ルームで 3,051 個の一致する一意なイベントを観測しました。独立したソケット比較を始める前に、一時ルームは明示的に退出しました。

サンプリングしたサービスメモリの最大値は 314.8 MiB でした。この計測付き実行の平均サービス CPU は 0.815 コアでした。これらの数値にはプロファイリング／ウォームアップ区間が含まれます。実行の集計 RTT p95 は 183–251 ms で、プロファイリング期間の数秒級の外れ値を含んでいました。約 50 ms の中央値だけを報告すると、それらの停止を隠してしまいます。TCP 設定の評価には、以下のクリーンでウォームアップ済みの比較を使ってください。

別のウォームアップ済みテストでは、同じ 4 つの接続を 2 つのルームで使い、35 秒の準備／ウォームアップの後に 30 秒のフェーズを 3 回行いました。プレイヤーは交互の移動入力だけを送ったため、これは戦闘スループットのベンチマークではなくトランスポートの比較です。その間、プロファイラーもアーカイブ転送も実行していません。

| クライアントが観測した指標                        |     元の設定 | 一時的な TCP_NODELAY | 元に戻した設定 |
| ------------------------------------------------- | -----------: | -------------------: | -------------: |
| 4 クライアント全体の RTT p50                      | 48.8–50.8 ms |          8.4–10.0 ms |   48.3–50.5 ms |
| RTT p95                                           | 52.1–54.4 ms |         10.6–13.2 ms |   51.0–54.1 ms |
| スナップショット到着間隔 p95                      | 57.6–58.2 ms |         18.4–18.6 ms |   57.7–58.0 ms |
| 入力送信 → 返却された state で観測される受信、p95 | 64.6–65.9 ms |         26.6–28.3 ms |   63.7–64.7 ms |
| サーバー更新処理 p95                              | 2.34–2.41 ms |         1.88–2.46 ms |   1.96–2.67 ms |

4 つのクライアントはすべてプロトコルエラーなしで接続を保ちました。オプションを戻すと遅延も戻り、サーバー処理は同程度の範囲に留まりました。この反転は独立したリリースを比較するよりも強い証拠になります。この構成では、バックエンドのソケットバッファリングが約 40 ms の回避可能なクライアント観測遅延を占めています。アプリケーションコードで最初に実装して検証すべき最適化です。

これらの変更は検証接続だけに影響しました。最終フェーズで元の設定に戻し、すべての検証セッションは明示的に退出しました。取得したアプリケーション、リスナーの既定値、サービス設定、Java ランタイムは変更されていません。サーバーは通常のプレイに利用できます。
