# MyGO!!!!! Fighter

TypeScript + React 製、Scala 3 サーバーで動作する対戦格闘ゲームです。原作のキャラクター、変身、15 ステージをそのまま収録し、ローカル対戦、CPU 戦、練習、設定可能な 1v1〜8v8 のリレー対戦に対応します。3 人乱闘では 3 人のファイターが同時に登場し、それぞれが 3 キャラクターを所持します（ローカルで 1P 対 CPU 2 体、またはオンラインで 3 人のプレイヤー）。撃破されたファイターは 5 秒後に自動で控えと交代し、バトルはそのまま続行します。ネットワークルームはリレーモードで 2 人、乱闘モードで 3 人に対応し、独立したルームを同時に複数稼働できます。

## 実行

Node.js 24 LTS（22.12 以上でも可）、JDK 21 以降、sbt をインストールします。その後、このフォルダーで次を実行します：

```sh
npm ci
npm run lan
```

初回ビルドでは JavaScript と JVM の依存関係をダウンロードします。サーバーのウィンドウは開いたままにしてください。ランチャーは JVM 成果物をビルドしてステージングし、本番と同じ 3 つのバックエンドロール——`rooms`、`lobby`、`edge`——を 3 つのローカルプロセスとして起動します。コマンドと出力は変わりません。ローカルアドレスとマシンの LAN アドレスを表示し、既定の公開ポートは **8080** です（rooms と lobby はループバックの 8091 と 8079 のまま）。トポロジーは[バックエンドサービス](docs/SERVICES.md)を参照してください。

Windows では `start-lan.cmd` をダブルクリックします。起動が成功しても失敗してもウィンドウは開いたままなので、エラーを確認できます。macOS/Linux では `./start-lan.sh` を実行します。これらのランチャーもアプリをビルドし、同じ Scala バックエンドロールを起動します。HTTP、静的ファイル、ルームディレクトリ、ルーム、WebSocket、権威対戦は Java が処理し、Node はビルドと起動のためのツールです。

Windows のフロントエンドビルドは、esbuild の一時ファイルを Git 管理外の `output/build-temp/` に置き、システムの一時ディレクトリでアクセス拒否によるクリーンアップエラーを避けます。これはランチャー、`npm run build`、`npm run build:pages`、`frontend/` から実行するビルドに適用され、システムの環境設定は変更しません。

Windows でローカルゲームサーバーを停止するには `stop-lan.cmd` をダブルクリックします。成功するとウィンドウは自動で閉じ、エラー時は開いたままです。スクリプトは 8080 ポートをリッスンしているのがゲームサービスであることを確認してから停止します。`PORT` も認識し、`stop-lan.cmd -Port 8181` で別ポートも指定できます。サーバーを閉じると接続中のプレイヤーは切断されます。停止スクリプトは Windows PowerShell を使用し、Node.js は不要です。

`scripts/stop-lan.ps1` は BOM 付き UTF-8 で保存してください。Windows PowerShell 5.1 が中国語のメッセージを正しく読むために必要です。`chcp 65001` はコンソールのコードページを制御するだけで、スクリプトファイルのエンコーディングを選ぶものではありません。

`npm start` を含むすべての起動コマンドは、`output/toolchain/` に既存のポータブル JDK と sbt ランチャーがあれば再利用します。互換性のある `JAVA_HOME` が優先され、システムに古い Java があってもポータブル JDK の利用を妨げません。この任意のローカルキャッシュは Git のダウンロード内容には含まれません。ない場合は上記の依存関係をインストールしてください。

Windows のランチャーは Java の一時ファイル（JLine のコンソール DLL を含む）を `output/java-tmp/` に置きます。Windows のユーザー一時フォルダーがアクセスを拒否した場合の起動エラーを避けるためで、管理者権限での起動やシステムフォルダーの権限変更は不要です。

一度ビルドすれば、`npm start` はフロントエンドを再ビルドせずバックエンドだけを起動します。ランチャーは JVM 成果物を再ステージングし、3 つのロールを起動し、バックエンドが応答するとプレイ可能なアドレスを表示します。MyGO サーバーがすでにある場合はそのアドレスを表示し、元のウィンドウのバックエンドを稼働させたままにします。戦闘ルールの変更を読み込むには、元のサーバーを閉じてから再起動してください。`PORT` で別ポート、`JAVA_HOME` で JDK を指定できます。ランチャーは macOS で一般的な Homebrew の JDK 21 も自動検出します。

## LAN 対戦

1. ホスト側の PC でゲームを起動します。両方の端末で表示された**LAN アドレス**を開きます（例：`http://192.168.1.20:8080`）。他の端末からホストの `localhost` アドレスは使えません。
2. **联机对战** を選択します。一方がルームを作成し、もう一方が 6 文字のルームコードを入力します。
3. ホストは **1v1–8v8** または **三人混战**、ステージ、地形を選びます。3 人乱闘では 3 人のプレイヤー全員が接続し、各自 3 キャラクターを選ぶ必要があり、全員の読み込みが終わるまでバトルは始まりません。**自定义对战规则** を展開すると、体力、BAN、無限エネルギー、無効化する攻撃を設定できます。ゲストにも同じルールが表示されます。オンラインロビーはローカル対戦と同じキャラクターカード、立ち絵プレビュー、順序付きの編成スロットを使います。BAN 数が 0 のときは各プレイヤーが自分の編成を埋め、スロットをクリックするとキャラクターを差し替えられます。3 人乱闘は BAN なしで、異なるプレイヤーのチーム間で同じキャラクターを使えます。
4. BAN を有効にすると、1P と 2P が設定された数のキャラクターを交互に BAN し、その後は交互に排他的にピックして両チームの編成が埋まるまで続けます。選べる BAN 数は両チーム分のキャラクターを確保します。更新や再接続でも進行状況は保持され、ホストは **重新禁选** で最初からやり直せます。両チームの編成が完了したら、2 人とも **准备开战** を押します。サーバーは両クライアントのアートワーク読み込み完了を待ちます。
5. 両プレイヤーとも **1P キー** で自分のキャラクターを操作します。

ローカル対戦と CPU 選択でも同じ[カスタムバトルルール](docs/CUSTOM_BATTLE_RULES.md)が使えます。既定は 200 体力と標準攻撃のままです。更新後は新しいルームと戦闘ルールを読み込むため、ホストを再起動してください。

ルールはほかに、時間無制限、30〜300 秒のラウンド、初期エネルギー、ダメージ／移動倍率、一撃必殺、吸血回復、低重力、空中ジャンプ無制限、ガード無効化にも対応します。**一击决胜**、**月面乱斗**、**吸血拉锯** のプリセットを試してから、個別の項目を調整してください。

百度 App と百度ブラウザーは、ネイティブプレイヤーが開かないよう奥義とフィニッシュの背景動画をスキップします。キャラクターアート、エフェクト、収録ボイス、フィニッシュのタイミングは通常どおりです。その他のブラウザーはインラインの背景動画再生を維持します。

両方の端末が同じネットワーク上でホストに到達できる必要があります。必要に応じてホストのローカルファイアウォールで使用ポートを許可してください。端末を隔離するゲスト Wi-Fi では接続できません。

Windows では、ファイアウォールが**実際にバックエンドを実行する Java 実行ファイル**を、アクティブなネットワークプロファイルとゲームの TCP ポートで許可する必要があります。Node だけを許可しても Scala サーバーはカバーされません。キャンパスや寮のネットワークは同じ Wi-Fi でも端末を隔離することがあります。ホストが自分の LAN アドレスを開けてももう一方の端末が開けない場合は、両方の端末を同じスマホのテザリングか個人ルーターに接続してみてください。

切断すると両プレイヤーが一時停止します。ページは自動で再接続し、同じタブを再読み込みしてもセッションが復元されます。両プレイヤーが再接続すると再開できます。ルームを離れるとそのセッションは無効になります。ルームは一時的で、サーバー再起動、30 分間プレイヤー操作がない場合、または 2 分間接続プレイヤーがいない場合に消えます。

## 公開オンライン対戦

両プレイヤーが同じ公開ゲームサーバーの URL を開き、**联机对战** を選んでルームを作成または参加します。別々のネットワークにいてもよく、どちらも 1P の操作を使います。各ルームは人間 2 人で、3v3 は順番に交代するチームリレーであり、6 人が同時に操作するわけではありません。

16 キャラクター全員が READY の前に、原作の全身立ち絵を使った短い入場演出を行います。開始時は入場演出が同時に再生され、3v3 では新しく出た控えだけが演じ、残っているファイターはリソースを保持します。ローカル対戦とネットワーク対戦は、一時停止／再接続からの復帰を含め、同じ 2.75 秒の開始カウントを共有します。「視差効果を減らす」設定では静的な紹介になります。

[阿里雲北京サーバー](https://mygo-123-57-149-254.sslip.io/)は**2 ルーム／4 人**に対応し、独自の HTTPS アドレスを持ち、GitHub Pages からのリンクはありません。両プレイヤーは同じサーバーを使う必要があります。デプロイ、制限、実測値は[公開サーバーの構築と運用](docs/WAN.md)を参照してください。公開アクセスには HTTPS、WebSocket 転送、ホストの受信 TCP 80/443 ルールが必要です。LAN ランチャーを実行するだけではこれらは設定されません。

## 操作方法

| 操作                | 1P / LAN            | 同じキーボードの 2P |
| ------------------- | ------------------- | ------------------- |
| 移動                | A / D               | ← / →               |
| ジャンプ / しゃがみ | W / S               | ↑ / ↓               |
| 3 段弱攻撃コンボ    | J                   | テンキー 1          |
| 強攻撃              | K                   | テンキー 2          |
| ブリンク            | L                   | テンキー 3          |
| 基本スキル          | U / I / O           | テンキー 4 / 5 / 6  |
| 変身（使用可能時）  | H                   | テンキー 7          |
| 必殺技              | P                   | テンキー 8          |
| 技一覧              | F1 または画面ボタン | 両者共通            |

後ろ方向を押し続けるとガード、後ろ + しゃがみで下段ガード、後ろ + U または前 + O で投げになります。方向 + スキルでキャラクター固有の技のバリエーションを選べます。2 回ジャンプすると二段ジャンプになり、下 + ジャンプで足場をすり抜けて落下します。タッチ操作は方向と攻撃の同時入力をサポートします。バトル中のツールバーから一時停止、再開、キャラクター選択への復帰ができます。

MewType の 5 キャラクターは、**下 + U** の飛び道具を追加で持ち、**共鳴 20** を消費します（2P：下 + テンキー 4）。アラレはハートの音波、リツは青いクマの和音、ミヤコは墨パネルの波、ユノは電子パルス、ノノカはウサギ耳のピックを放ちます。元の U/I/O スキルも使用できます。波はガードでき、相手の飛び道具と衝突し、高い地面で止まります。通常攻撃のヒットで共鳴が 10、スキルのヒットで 2 回復します。HUD の 2 本のバーには現在値（最大 100）が表示されます。

Mujica の **H 変身** は共鳴 50 を消費し、20 秒間続きます。変身時に近距離の爆発を 1 回放ち 10 ダメージ（ガード時は 2）を与え、その後、色付きのオーラがステージ衣装を包む間、**ダメージ 1.2 倍** と **移動速度 1.1 倍** を得ます。この爆発では共鳴は回復しません。両方の効果は変身の終了とともに消えます。

## モバイルブラウザー

デスクトップ、スマホ、タブレットの対戦は、既定で利用可能なビューポートいっぱいにアリーナを表示します。**登台对战**、**准备开战**、**继续对战** をクリックすると、そのプレイヤーの操作（ジェスチャー）内でブラウザーの全画面を要求します。**Esc** または浮動の **退出** ボタンで全画面を終了します。ポーズメニューからは再開、キャラクター選択、ヘルプ、技一覧、オーディオ設定に進めます。バトルを離れると画面の向きのロックが解除され、ブラウザーの全画面も終了します。ブラウザーのポリシーによって全画面要求が拒否されることがありますが、ビューポートのレイアウトのままプレイできます。

タッチ端末では、左側のスライド式親指スティック（左右移動、上でジャンプ、下でしゃがみ、斜め入力にも対応）と、右側の四角い攻撃・スキル・必殺技・変身ボタンを使います。スティックとボタンは同時タッチに対応し、ポインターキャンセル、キャプチャー消失、アプリ切り替え時には押されているコントロールが解放されます。ノッチやホームインジケーターにはセーフエリアの余白が入ります。縦向きと横向きのどちらでもプレイでき、横向きが最も広いアリーナになります。オンライン対戦中は、ツールバーを隠しても実測の **ms RTT** が表示されたままです。ローカル対戦ではネットワーク遅延がない旨が表示され、接続断や更新停止にも明示的なステータスメッセージがあります。

Fullscreen API を提供するブラウザーにはナビゲーション UI の非表示を、タッチ端末には横向き固定を要求しますが、対応していないモバイルブラウザーもあります。アプリは `display: standalone` と Apple Web App メタデータを持つ相対パスの Web マニフェストを提供します。ブラウザーのメニューから **Add to Home Screen / 添加到主屏幕** を選び、インストールしたショートカットから起動すると、対応環境ではブラウザーのツールバーなしでプレイできます。全画面が使えないときは短いヒントが表示されます。これはオフラインプレイを提供するものではありません。すべてのブラウザーのツールバーを強制的に消す確実な方法は Web ページにはありません。[Fullscreen API の要件](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen)と[マニフェストの display モード](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/display)を参照してください。

ローカルとオンラインのキャラクター選択は、ビューポートサイズのレイアウトと固定の確認フッターを使います。デスクトップでは 16 ファイター全員を同時に表示し、コンパクトなタッチカードは縦向きでも横向きでもロスター全体に到達できます。極端に低い画面では中央の選択エリアだけがスクロールし、**登台对战**、**准备开战**、ドラフトの確認は常に見えます。ステージのサムネイルは横にスクロールし、原作のステージとルールはすべて利用できます。

## 開発

```sh
npm run dev            # Vite フロントエンド、ポート 5173。API/WebSocket はポート 8080 へプロキシ
npm run build          # 厳格な TypeScript チェック、本番 UI、共有戦闘カーネル
npm run build:pages    # GitHub Pages 用の静的ブラウザーバージョン。JVM サーバー不要
npm run package:server # UI/カーネルとデプロイ可能な Scala/JVM ディストリビューションをビルド
npm run stage          # JVM ディストリビューションをステージングのみ（起動しない）
npm start              # 本番ビルドを配信する 3 つのローカルバックエンドロール
npm run check          # TypeScript、メディア、プロトコル、サービス境界のチェック
npm run check:api      # 登録済み API 名、フロントエンドの呼び出し元、プロトコルバージョン
npm run check:services # サービスフォルダー、内部契約、systemd ユニット
npm run check:e2e      # 3 つのローカルロールプロセスを起動し、ルームを端から端まで確認
npm run check:backend  # Scala のコンパイルとフォーマットチェック
npm run format         # フロントエンド、スクリプト、ドキュメントを整形
npm run format:backend # Scala ソースを整形
```

Vite で開発するときは、別のターミナルで `npm start` を実行して API を提供します。共有戦闘ルールを編集したら、JVM に埋め込まれたカーネルを更新するために再ビルドし、バックエンドを再起動してください。

本番フロントエンドは React を別の共有チャンクに分け、ゲームのバンドルを Vite の既定の 500 kB 警告しきい値以下に保ちます。サーバーのパッケージングはメンテナーを宣言し、API ドキュメントの成果物を除外します。ランタイム jar と Web アセットをまとめます。API ドキュメントは `node scripts/scala.mjs doc` で別途生成します。Scala 3.3.6 では Cats Effect 3.6.3 が継承する `IOApp` のドキュメントに未解決リンクが報告されることがありますが、コンパイルやサーバー実行には影響しません。コンパイルでは `-Werror` が有効なままで、使用しない Scaladoc の段階でのみ省略されます。

## コードマップ

- `frontend/src/pages/GamePage/index.tsx`：ページの骨格。ページコンポーネント、hooks、状態オブジェクト、エフェクトはその近くにあります。
- `frontend/src/game/engine.ts`：対戦状態と公開の戦闘 API。`game/match/` はルール実装を責務ごとに分け、`game/data/` はバンド横断のデータを組み立て、`game/bands/<band>/` がそれぞれのロスター、技、形態を所有します。共有戦闘カーネルはブラウザーのグローバル、ネットワーク呼び出し、Node 依存を持ちません。
- `frontend/src/pages/GamePage/runtime/`：ページの調整、オーディオ、入力、ネットワーク、ブラウザー表示のアダプター。配下の `rendering/` が画像デコード、アニメーション、カメラ、バトルエフェクト、情景を担当します。
- `frontend/src/assets/`：マニフェストの読み込み、メディア種別、バンドアートの検索。起動処理とページ表示で共有されます。
- `frontend/src/apis/rooms/`：登録済みの Scala ルームメッセージごとに 1 つの HTTP 呼び出しと、永続的なソケット接続。
- `backend/src/main/scala/services/rooms/`：ルームメッセージ、ドメインオブジェクト、登録、120 Hz のルームランタイム、ソケット境界。ライブルーム状態の唯一の所有者です。
- `backend/src/main/scala/services/lobby/`：インスタンスレジストリ、グローバルのルーム予算、配置、ルームコードディレクトリ。
- `backend/src/main/scala/services/edge/`：公開の受け入れ制限、静的ファイル、API 転送、所有者キャッシュ、WebSocket プロキシ。
- `backend/src/main/scala/services/system/`：ロールのディスパッチと Cats Effect の起動、アプリケーションリソース、共有ルーティング、静的配信。プロセス間のペイロード型は `objects/internal/` にあります。
- `frontend/public/`：メディアマニフェストとキャッシュ可能なランタイムアセット。
- `assets/`：`assets/characters/<band>/` のソースアートと共有機能フォルダー。設計メモは `assets/notes/` にあります。[アセットカタログ](assets/README.md)を参照してください。
- `scripts/` と `tools/`：アプリのビルド／起動コマンドと任意の Python アートパッカー。[アートワークのワークフロー](docs/ARTWORK.md)を参照してください。

Scala バックエンドは 1 つのリリース成果物から `edge`、`lobby`、`rooms` のロールとして動作し、各 rooms プロセス内の制限された GraalJS コンテキストに**同じ TypeScript 戦闘カーネル**を埋め込みます。ルームの実行、信頼済みセッションの解決、認可、ライフサイクル、並行性、トランスポートは Scala が担います。戦闘ルールを共有することで、16 キャラクターに対して分岐する 2 つの実装を避けています。これは明示的なアーキテクチャの選択であり、すべての戦闘計算を Scala へネイティブ移植したものではありません。エンジンとキャッシュされたソースはアプリケーションリソースで、各ルームは独立した制限付きコンテキストを保持します。公開サーバーは TCP_NODELAY を有効にしています。計測値と本番の Java 選定は[ランタイム評価](docs/RUNTIME_OPTIMIZATION_2026-10-27.md)を参照してください。

[バックエンドサービス](docs/SERVICES.md)、[アーキテクチャとレビューガイド](docs/ARCHITECTURE.md)、[コースガイダンス](docs/COURSE_GUIDANCE.md)、[LAN プロトコルとタイミング](docs/LAN.md)も参照してください。付属のスタイルルールは [STYLE_RULES.txt](docs/STYLE_RULES.txt) に保持されています。

`main` へプッシュすると、GitHub Pages が `frontend/dist` の React ビルドを自動で公開します。静的ビルドはローカル対戦、CPU、練習、3v3 に対応します。ネットワークルームには Scala サーバーが必要です。任意のリポジトリ Actions 変数 `PUBLIC_GAME_URL` を設定すると公開サーバーへのリンクを有効にできますが、今回の試験では未設定です。ローカルの静的ビルドでは `VITE_PUBLIC_GAME_URL` を使用できます（`frontend/.env.example` を参照）。原作のランタイムメディアはすべて保持され、パスはアプリからの相対で解決されるため、プロジェクトのサブパス URL でも動作します。

テストスイートは削除されています。公開前に上記のチェックと 2 つのビルドを実行し、ブラウザーでプロジェクトサブパスの読み込み、収録音声、キャラクターの変身、必殺技、メニューの流れを確認してください。LAN 関連の変更では、同じ Scala サーバーに対して 2 つのクライアントが参加し、読み込み、対戦、一時停止、再接続できることも確認します。ローカルのレポートやスクリーンショットは Git 管理外の `output/` フォルダーに置いてください。
